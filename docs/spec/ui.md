# 8. UI details

Part of the Lectrix specification. [AGENTS.md](../../AGENTS.md) holds the rules every change follows and [README.md](README.md) lists these files; sections keep the numbers they share, so "section 5.4" is in AGENTS.md and "section 6.5" in [annotations.md](annotations.md).

## 8.1 Layout

- **Windows:** a tab can have a window of its own, and windows exchange tabs. Dragged off its row (24 px above or below it, or out of the window at a side), a tab is on its way out: a stand-in with its name follows the pointer while it is over the window, the tab waits dimmed in its place, and going back to the row takes it up again. Dropped outside its window, on another Lectrix window it joins that window's tabs at the end and is shown there, and anywhere else it gets a new window with its title bar under the pointer, the size of the one it left. Dropped inside its window, it stays where it was and is shown (near an edge of the pages, it goes beside them instead: section 6.1, split view). Esc ends the drag and the tab stays. The tab's context menu and File > Move tab to new window (a new window a little down and right of the first; a command without a default shortcut) do the same from the keyboard. The document goes as it is: unsaved changes, undo history, its place, zoom and page display; nothing asks to save. A window's only tab can't go to a new window (it would be the same window again), but it can go to another one. A window left with nothing to show closes; one that still has the Combine view stays. Every window is the whole app (menus, start screen, Settings, its own Combine view), windows exchange tabs (ADR 0016), and none is the main one: closing a window asks about its own unsaved documents and closes them, Lectrix quits with its last window, and File > Exit closes them all, each after its own question (Cancel in any of them keeps that window and the one Exit was picked in). Settings apply to every window at once, and the recent files are the same in all. The taskbar names each window after what it shows ("report.pdf - Lectrix"; "Lectrix" on the start screen).
- **Window:** Lectrix starts where its window was when it last closed (with several windows, the one used last): the same size and position as a normal window, maximized if it was (then Restore goes back to that size), never minimized. Kept in app data with the panes; a place on a monitor that is no longer there, or with the title bar out of reach, is dropped and Windows places the window. The window is made there, so it never shows at the default size first.
- **Title bar:** custom (explicit drag region), holding the app's icon and name at the left, the menus, the document tabs with a + button after them (File > Open) and the window buttons, placed and drawn as each platform's own apps have them (ADR 0021): on Windows drawn by the app at the right (Tauri decorations off), as Windows draws them; on Linux drawn by the app in Adwaita's style (round, 24 px, a faint fill), the buttons and the end GTK's decoration layout names (GNOME: close alone, at the right); on macOS the system's own traffic lights over the bar's left end, which leaves 80 px for them (none in a full-screen space, where the system hides them). On macOS the menus are not in the title bar but in the system's menu bar, arranged as Mac apps arrange theirs (`menus.svelte.ts`, laid out once for both; `menu.rs`): the application menu (About, Check for updates, Settings, Services, Hide, Quit), File, Edit (Undo and Redo, which edit a focused text field's text too, then the system's Cut, Copy, Paste and Select All, and a Find submenu), View, Document, Window (Minimize, Zoom, the tab commands, Bring All to Front) and Help, with labels in title case. Each window sends its menus as they change, and the menu bar shows those of the window in use. While a dialog is open, the menu bar offers nothing that acts on the window. The bar is measured as VS Code's title bar (35 px tall, 16 px icon in a 35 px box, 12 px name, 13 px menus). The icon and name are one button, which shows the start screen while something is open (section 6.1; filled under the pointer; plain while the start screen shows, with the pointer on it or not, since there it is where one is) and still moves the window when dragged; with nothing open it only moves the window.
- **Side panes** hold three panels: Pages (thumbnails), Bookmarks and Annotations (the annotation list). The left pane, open by default, starts with the first two; the right pane, closed by default, with Annotations. View > Pages, Bookmarks and Annotations (commands without a default shortcut) show their panel, checked while it is on screen, and close its pane when it is already shown. View > Side panes (F4; on macOS ⌥⌘S) hides both panes while either is open, and shows each pane that has a panel while both are closed; it is checked while either is open. Each pane's top row, with a line under it, has its panels' tabs (icons with tooltips and accessible names, drawn as the annotation tools are: the panel shown has the active tool's mark, which glides to the tab picked in 140 ms, at once with reduced motion) and, at its outer end, the button that hides it. A closed pane's button stays in the same place, at that end of the view bar's row, as in Obsidian. Panels move freely: a tab is dragged along its row, into the other pane's row, or onto a closed pane's button; Ctrl+Shift+Left/Right and the tab's context menu do the same from the keyboard, crossing between the panes at their inner ends. A panel moved into the other pane is shown there; a pane left without panels closes, and its button goes until a panel is dragged to the drop place shown there.
- **View bar**, one bar at the top of the document as in Acrobat, in the side panes' colour and continuous with their top rows (the line between a pane and the page starts below them), its contents centered: previous page, next page, the page box with the page label or number and the physical position after it ("iv" then "(4 of 312)", or "4" then "of 312"; an empty box then "(4 of 312)" on a page whose label is empty, section 6.3; screen readers hear "iv (4 of 312)"), then zoom out, the zoom box and zoom in, then the page display (a menu of the scroll modes and the cover page, section 6.1), then the visual adjustments (a panel, section 6.1), then the annotation tools when docked there (Settings). Previous and next page go to the top of that page (in the two-page modes, the next row), gliding there (section 6.1), and are not recorded in back/forward history. In a narrow window the bar wraps onto a second row.
- **Center:** the page canvas, below the view bar. The annotation toolbar is docked or floats (Settings). Docked, it is in the view bar, or in a bar of its own at the left or the right of the canvas: in the view bar's colour, from the view bar down, between the canvas and that side's pane, with a line between it and the pages. Floating, it lies over the canvas, centred along its bottom, top, left or right edge (at the right, clear of the pages' scrollbar). Its colour button comes first, before the tools (after the page and zoom controls in full screen). At a side, docked or floating, its controls are stacked: the colour, then the tools one under another, then the style controls the tool brings. There the colour button shows the colour alone and a size's button its number alone ("2" for 2 pt; the list names the sizes in full), each as wide as a tool, and what a control opens (the colours, a list of sizes) goes beside the toolbar, over the pages, never over the tools under it. Where the canvas has less height than a stacked toolbar needs, the toolbar scrolls, with no scrollbar of its own. The search bar and the bookmark inspector move below a floating toolbar that stays at the top, and beside one that stays at the right. The active tool has an accent icon and an accent border on every side; so do the type buttons of a selected annotation. Picking another tool (or type) glides that mark to it in 140 ms, and the style controls the tool brings (stroke width, font size) slide open after the tools (beside them, or under them in a stacked toolbar); reduced motion does both at once. Full screen (section 6.1) shows the page canvas alone, on the whole screen, with the toolbar floating and the side panes over the pages when something brings them.
- The Annotations tab carries the "needs repair" dot, and so does its pane's button while that pane is closed.
- **Inspector**: for a bookmark, floating over the pages beside its row in the Bookmarks panel (section 6.2); for an annotation, a panel beside it on the page that can be dragged and resized (section 6.5). Shown when opened for it; an annotation's, like its bar, is not shown while the annotation list shows its row, which has its controls and its comment.
- **Side panes** resize by dragging their inner edge, or from the keyboard on that edge (arrows, Home, End); a double-click resets the width. Each takes at most 40% of the window. Every other pane beside the pages resizes the same way, with the same edge (`PaneResizer.svelte`), and has its width remembered: the Combine view's files (section 6.4). Which panes are open, their widths, the panels each holds and the one each shows are remembered in app data. Opening and closing slides (140 ms); a fit-width or fit-page view re-fits as a pane moves and renders again once it stops.

## 8.2 Controls

- As in Neo: document tabs are pills, the active one raised; menus, popovers and dropdown lists are flat, with a thin edge and no shadow; a notification, and the update notice above them, has the thin edge and a slight shadow (`.notice`), which lifts it off the pages it lies over; clickable controls show the hand cursor (the window buttons keep the arrow). A coloured button (the primary one, filled in the accent, and the destructive one, in the red of errors) stays in its colour under the pointer, a shade further from its text: darker under the light theme's white text, lighter under the dark theme's dark text (`--lectrix-accent-hover`, `--lectrix-danger-hover`). A menu item whose submenu is open, and a button whose menu or panel is open, keep the tint they have under the pointer while the pointer or the focus is in what they opened. Dropdowns are the app's own (`Dropdown.svelte`), never the native `<select>`, whose list the system draws in its own colours. Sliders are too (`Slider.svelte`, for every slider: the comment tooltip's delay, an annotation's opacity): a thin track with no outline, filled up to the handle in the accent, as a switch that is on, and a round handle in the colour of that switch's thumb (white, in the dark theme as in the light one) with a thin edge in the accent and a slight shadow, each colour a token of its own. The fill and the handle glide to each new step in 100 ms.
- Tooltips are the app's own as well (`Tooltips.svelte`): a control names its tooltip in `data-tip`, never in `title`, which the system would draw in its own style (a test checks that no component has one). A tooltip is flat, in the menus' colour with their thin edge, and has a small tail with curved sides, as the comment panel's, pointing at its control. It goes below the control and centred on it, above it when there is no room below, beside it when there is none above either (a pane's edge), and stays inside the window; for a control wider or taller than 320 px (a row, a pane's edge) it goes where the pointer is along it, clear of the cursor's arrow. It shows once the pointer has rested on the control for half a second, or when Tab or an arrow key brings the keyboard focus there, and at once within 0.4 s of another tooltip going; it fades in in 100 ms. A press, a key, scrolling or leaving the control takes it away, and after a press or a key it stays away until the pointer leaves that control. Screen readers get a focused control's tooltip as its description, unless it only repeats the control's name. An annotation's comment tooltip (section 6.5) has the same look.
- A side panel with nothing to list (`PanelEmpty.svelte`: the Bookmarks panel, the annotation list) shows, centred a third of the way down the panel, the panel's icon in a soft 40 px circle (the hover tint, the icon muted), a short title, one muted line on what to do, and a button for it where there is one. A shortcut in the line or the button is shown as a key, in the look of Settings' shortcut keys, as Settings has it (none when it has been taken away). What each panel says is in its section (6.2, 6.5).
- Esc that closes a menu or a dialog does that and nothing more: it doesn't also take the app's step back (clearing selected text, deselecting an annotation, picking the Select tool; `onKeyDown` in `App.svelte`).
- A list, panel or dialog that scrolls only up and down never scrolls sideways, even when its content is a pixel too wide: it sets `overflow-x: hidden` beside `overflow-y: auto` (a test checks), so a touchpad's diagonal swipe moves it only up and down. A scroller that may scroll both ways (the start screen, Compress's preview) hides the overflow of an axis its content does not overflow by more than a pixel (`scrollAxes`; a test checks every `overflow-auto` has it, or its own style), and the pages hide the sideways overflow while they fit the view's width and the up-and-down one while they fit its height.

## 8.3 Motion

- Document tabs come and go in 140 ms (`tabmotion.ts`): a new tab grows from nothing to its width as it fades in, and a closed one shrinks away as it fades out (its width, padding and the gap after it closing with it), so the tabs beside it slide over without a jump. A tab on its way out is no tab any more: not in the tab list for screen readers or the keyboard.
- Notifications come and go in 140 ms (`noticeMotion` in `components/notices.ts`), by a zoom, not a slide: one is where it belongs from its first frame, and grows there from 90% of its size as it fades in; dismissed or timed out, it shrinks to that as it fades out. Its place in the column opens ahead of it and closes after it, so the ones above it make way and close up without a jump. The update notice comes and goes the same way.
- A dialog comes in in 140 ms: it rises 8 px into place as it fades in, while the window behind it dims. It goes the same way back in 100 ms, and takes no clicks meanwhile. On macOS a dialog is a sheet instead (ADR 0021): it comes down 16 px from under the title bar into place just below it, centred across the window, over a light dim, with 12 px corners and 28 px buttons, the main one at the right; a question is an alert as macOS lays them out (the app's icon over a centred title and message, buttons as wide as the alert, two side by side with the main one at the right, more stacked with it on top and Cancel at the bottom), and Return presses the main button. It goes on showing what it showed (`held` in `components/held.svelte.ts`): the question that was answered, the progress last reported; what its buttons and forms act on is gone by then, so a second press does nothing.
- The start screen's tool cards move more slowly than the rest of the app (ADR 0030): a card lifts in 250 ms, its icon tile rises with a small spring in 400 ms, and a press's ripple runs for 400 ms; colours and fades take 150 ms (section 6.1, start screen). With reduced motion the states change at once and no ripple runs.
- Progress bars are one component (`ProgressBar.svelte`: copying pages into a new file, checking for an update, downloading one): the filled part glides to each new value in 140 ms, and a sheen runs along it, so the bar is seen to be at work between two values too; while how far is not known, a third of the bar runs from end to end. These two go on for as long as the work does; reduced motion stills them.

## 8.4 Shortcuts on other keyboards and on macOS

The default shortcuts are listed in section 8.5. With a keyboard layout that types non-Latin letters (Russian, Greek...), letter shortcuts follow the key's place on a US keyboard, so Ctrl+Я is Ctrl+Z; Latin layouts such as AZERTY or Dvorak use the letter typed. On macOS, Ctrl in a shortcut is the Command key (the Control key answers to it too, and is the one meant with Tab, since Command+Tab switches apps), shortcuts are shown as the system shows them (⇧⌘S, ⌃⇥), Command with H or M (and Option+Command+H) belong to the system and can't be given to a command, and some commands come with the keys Mac apps use (`mac` in `shortcuts.ts`): Quit ⌘Q, Close ⌘W alone, Redo ⇧⌘Z first, Find next and previous ⌘G and ⇧⌘G, Go to page ⌥⌘G, Back and Forward ⌘[ and ⌘], Full screen ⇧⌘F (F11 is the system's there).

## 8.5 Visual style, behavior, accessibility and default shortcuts

**Visual style.**

- Colours from Neo, the Obsidian theme: its light theme and its Midnight dark theme, with the greys tinted to Lectrix blue's hue, solid throughout (no Mica; ADR 0014).
- Follow the system light/dark setting by default; Settings can force light or dark. The accent is Lectrix blue from the brand kit (ADR 0010): `#2F5DAA` in the light theme, `#6FA3EF` in the dark one.
- As in Neo: document tabs are pills, the active one raised; menus, popovers and dropdown lists are flat, with a thin edge and no shadow; notifications have a slight shadow; clickable controls show the hand cursor.
- Controls are the app's own, never the system's (8.2): dropdowns (`Dropdown.svelte`, never `<select>`), sliders (`Slider.svelte`) and tooltips (`Tooltips.svelte`: a control names its tooltip in `data-tip`, never in `title`, and a test checks).
- Font stack: Google Sans, bundled with the app (ADR 0009), then Segoe UI Variable, Segoe UI and the system UI fonts for characters it lacks.
- Spacing on an 8 px grid (4 px for tight spots); corner radius 6–8 px; thin borders instead of heavy shadows.
- All colors, sizes and radii as CSS variables (design tokens) consumed by Tailwind; no hard-coded colors in components.

**Behavior.**

- Never block the UI thread. Long operations (combining, repair, saving a large file) show progress and can be canceled.
- Placeholder page shapes at the correct size while pages render, so the scroll position never jumps.
- Errors in plain language with a suggested next step; never show raw error text or crash on bad input. Log details to a rotating log file.
- Respect reduced-motion settings; keep animations under 150 ms (the start screen's cards excepted, ADR 0030). Notifications, dialogs (sheets on macOS) and progress bars each move in one way, in one place (8.3).

**Accessibility.** Every control is reachable by keyboard with a visible focus ring (the page canvas, which takes focus to scroll from the keyboard, has none: a ring around the document is noise; nor have What's new's list of changes, which takes the focus as the dialog opens for the same reason, and the About dialog, which takes it itself), has an accessible name, and meets WCAG AA contrast (checked by `src/lib/contrast.test.ts` in both themes). Shift+F10 and the Menu key open the focused control's context menu. App-wide shortcuts such as Ctrl+S work while typing in panel fields.
