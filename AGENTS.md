# Lectrix — Instructions for Coding Agents

Oct 4, 2026 · @Mark

## 1. Mission and scope

Lectrix is a lightweight, open-source PDF editor for Windows, designed to go cross-platform later, whose annotations, bookmarks and page labels open correctly in Acrobat and every other mainstream reader. Interoperability is the product's core promise: a feature that works only inside this app is a failed feature.

This document is the single source of truth for the product and for how to work on it. Read it in full at the start of every session. v1 is complete (2026-10-04); `docs/status.md` lists its measurements and known gaps. The name is **Lectrix**; the frontend keeps it in one config constant (`APP_NAME` in `src/lib/config.ts`).

**v1 contains:**

- **Viewer:** fast continuous scrolling, zoom, thumbnails, text selection, text search, tabs for multiple documents, which can be spread over several windows.
- **Bookmarks:** create, rename, reorder, nest, delete, and retarget the document outline.
- **Page labels:** assign label ranges (roman front matter, arabic body, prefixed appendices).
- **Stitching:** combine several PDFs into one, at page level, with bookmarks and labels merged sensibly.
- **Annotations:** highlight, underline, strikeout, squiggly, sticky note, freehand ink, text box, plus an annotation list.
- **Repair annotations:** normalize broken annotations written by other apps so they display everywhere.

**Not in v1** (do not build, even partially, without the user's go-ahead): form filling, digital signing, OCR, editing page text or images, redaction, converting other formats to PDF, cloud sync, mobile builds.

## 2. Tech stack and constraints

The stack is fixed: Tauri 2, a Rust backend running MuPDF, and a Svelte 5 frontend styled with Tailwind. Versions are pinned exactly and recorded in `docs/versions.md`; upgrade deliberately and update that file.

| Layer | Choice | Notes |
| --- | --- | --- |
| App shell | Tauri 2 | WebView2 on Windows. Bundled with the Tauri bundler (an NSIS installer, ADR 0020). |
| Backend language | Rust, stable toolchain | All PDF logic lives here. |
| PDF engine | MuPDF (C library) | Via the `mupdf` Rust crate, vendored and patched in `third_party/mupdf-rs` (ADR 0001); `mupdf-sys` comes from Lectrix's fork (ADR 0008). The C API is called directly through `mupdf-sys` where the crate lacks coverage. |
| Frontend | Svelte 5 (runes) on SvelteKit | `adapter-static`, SSR disabled, as Tauri's own SvelteKit guide recommends. TypeScript in strict mode. |
| Styling | Tailwind CSS | Through its Vite plugin. Design tokens as CSS variables. |
| UI primitives | Bits UI (headless) and Lucide icons | Headless only, so the visual design stays ours. |
| Rust/TS type sharing | `ts-rs` | TypeScript types for every IPC command and payload are generated (`cargo test -p lectrix`); never hand-write them. |
| Testing | `cargo test`, Vitest, `tauri-driver` with WebdriverIO | See section 9. |

**Hard constraints:**

- **License:** the whole project is AGPL-3.0-or-later, because MuPDF is AGPL. Every new dependency must be AGPL-compatible (MIT, Apache-2.0, BSD, MPL-2.0 are fine). Maintain `THIRD_PARTY_NOTICES.md`; `tests/licenses/notices.py` checks every shipped package and regenerates `THIRD_PARTY_LICENSES.md`. The About dialog shows where the source is published (`SOURCE_URL` in `src/lib/config.ts`).
- **Platforms:** Windows 10 (1809+) and Windows 11, x64 first. Anything Windows-specific goes in a `platform` module behind a trait, so macOS and Linux can be added without touching feature code.
- **Network:** none at runtime except the update check and download from Lectrix's GitHub releases (ADR 0011): once a day, which Settings can turn off, and when the user picks Help > Check for updates. No telemetry, and the webview never goes online. A web link the user clicks in a document, like the links in About, is handed to the system's browser (section 6.1); Lectrix itself fetches nothing.
- **Security:** minimal Tauri capabilities. File access only to paths the user picked through a dialog, drag-and-drop, or file association. Strict CSP, no remote content in the webview.
- **Performance targets** (a regression is a bug; the latest measurements are in `docs/status.md`): window visible in under 1 s; first page of a 500-page PDF visible in under 1 s; no blank page visible for more than 200 ms while scrolling; idle memory under 200 MB with one large document open (for `lectrix.exe`; WebView2 has its own rule, ADR 0002).

## 3. Architecture

All PDF reading and writing happens in Rust through MuPDF; the Svelte frontend never parses or modifies PDF bytes. The frontend displays rendered pages and draws interactive overlays, and every change it makes is a typed operation sent to Rust.

&#91;embedded content: architecture · three layers over MuPDF\]

Down-arrows carry typed operations and calls; up-arrows carry page images, revisions and results.

**Three layers:**

1. **`pdf-core` crate** (plain Rust library, no Tauri dependency). Owns document sessions, rendering, text geometry, the annotation write profile, outlines, page labels, merging, repair, undo/redo, saving and crash-recovery copies. Everything in it must be testable headless.
2. **`src-tauri` app crate.** A thin layer: IPC commands that call `pdf-core`, the page-image protocol, file dialogs, menus, window effects, file association, recovery slots, app state, logging.
3. **SvelteKit frontend.** Views, editors, overlays and UI state only.

**Threading.** MuPDF contexts and documents must not be shared across threads without care. Each open document has its own actor thread that exclusively owns its MuPDF document; commands reach it through a channel and get replies back. For parallel rendering, build a display list per page on the actor thread, then render display lists on a small worker pool with cloned contexts, as MuPDF's multi-threading guide describes. ADR 0001 records the crate's thread-safety findings.

**Rendering pipeline.**

- The frontend requests pages through a custom URI protocol: `lectrix://page/{docId}/{pageIndex}?scale={s}&rev={r}`. Including the document revision in the URL makes cache invalidation automatic. `&hide={n},{n}…` names annotations to leave out of the image, by object number: the ones the annotation list filters out (section 6.5).
- Rust renders the page with MuPDF and returns a PNG at the fastest compression level (ADR 0004). Raw RGBA drawn into a `<canvas>` stays available for measurement (`LECTRIX_IMAGE_FORMAT`).
- Above a zoom threshold, render 512 px tiles instead of whole pages.
- The start screen's grid gets recent files' first pages from `lectrix://recent/{index}?w={px}&opened={ms}`: rendered from the file on disk without opening it as a document, named by the file's place in the recent list and the time it was opened (never by a path from the webview), and kept in memory while the file's size and modification time are unchanged.
- Keep an LRU cache of rendered images keyed by document, page, scale bucket and revision, with a configurable memory cap.
- Mount only pages near the viewport (a quarter screen above and below, ADR 0002); show a sized placeholder for the rest. Thumbnails wait while pages on screen render.
- Render ahead: once the view has rested for 120 ms, the frontend has Rust render the row of pages after the mounted ones and the row before them into the image cache (the page URL with `&warm=1`, which answers with no image), so a page scrolled or turned to is there already; a scanned page takes a quarter of a second to render. These pages are not mounted, so the webview holds nothing of them, and their requests wait while pages on screen render, as thumbnails do. One row each way and no more: each page rendered ahead takes its place in the image cache and in MuPDF's store from pages already seen.
- An image is never rendered twice at once (`Renders` in `protocol.rs`): a second request for it waits for the first and takes its result from the cache. The first tile of a page at a scale renders alone, since it decodes the page's images, which MuPDF then keeps for the other tiles.

**Text geometry.** For text selection and highlights, Rust extracts MuPDF's structured text per page (characters with their quads) and sends it to the frontend once per page and revision. The frontend does hit-testing and selection locally against that cached geometry, then sends the selected character range back with the highlight operation, so Rust computes the final quads. A page's links (`pdf-core/src/links.rs`: where each is, and its target resolved as a bookmark's is) come with its text, and the frontend finds the one under the pointer the same way.

**Windows.** Every window is the whole app with tabs of its own (section 8): the first is `main`, later ones `window-2`, `window-3`… All share the one process, its documents and its app data. `src-tauri/src/windows.rs` keeps which window shows which document; moving a tab to another window changes only that (`move_document`), the session with its unsaved changes and undo history staying as it is, and the window that gets the tab asks for it (`list_open_documents`). Rust sends an event to the window it concerns (`emit_to`), and the frontend listens through its own window (`listen` in `src/lib/ipc/index.ts`), since a plain listener would hear every window's events. A window's documents close when it is destroyed; Lectrix quits with its last window.

**IPC surface.** Commands live in `src-tauri/src/commands.rs`, all typed, among them `get_document_info` (page count, page sizes and rotation, outline, page labels, annotation list), `get_page_text`, `search_text`, `apply_operation`, `undo`, `redo`, `save`, `save_as`, `plan_merge`, `execute_merge`, `extract_pages`, `scan_annotations_for_repair` and `repair_annotations`. Every mutating command returns the new document revision plus the changed data, so the frontend never re-fetches everything. The webview can call only the commands it is granted: a new one is declared in `src-tauri/build.rs` and granted in `src-tauri/capabilities/default.json` (a test checks both), or calling it fails at run time.

## 5. Annotation interoperability contract

Every annotation this app writes must display, print and be editable in Acrobat Reader, PDFium-based viewers (Edge, Chrome), pdf.js (Firefox) and Foxit. Write conservatively, read leniently, and never weaken these rules to make a test pass: report the conflict instead. Mirror this section in `docs/interop-profile.md`, which also records where each rule is enforced and tested.

### 5.1 Write profile (mandatory for every annotation written or edited)

1. **Standard subtypes only:** Highlight, Underline, StrikeOut, Squiggly, Text (sticky note), Ink, FreeText. No custom subtypes and no private keys.
2. **Appearance stream always.** Every annotation gets a normal appearance (`/AP /N`), regenerated after every edit, using MuPDF's appearance synthesis with the corrections in ADR 0006. If MuPDF's appearance for a type fails the interop tests (section 9), write a custom appearance stream for that type in `annot/` and document why in an ADR.
3. **QuadPoints in Acrobat order.** For text-markup types, each quad is written as upper-left, upper-right, lower-left, lower-right, in PDF user space. This is the de facto order Acrobat uses, not the counter-clockwise order the spec text describes. One function writes quads, with unit tests. Upper and lower, left and right are as the glyphs stand, in right-to-left text too (ADR 0017).
4. **Rect contains everything.** `/Rect` is the union of all quads, ink paths, or the text box, plus the stroke width and a 1 pt margin.
5. **Highlights blend.** Highlight appearance streams use an ExtGState with Multiply blend mode so text stays readable. Store opacity in `/CA` on the annotation as well as in the appearance.
6. **Complete metadata:** `/NM` (a UUID), `/T` (author, from settings, defaulting to the Windows user name), `/CreationDate` and `/M` (PDF date strings with time zone), `/F 4` (Print flag), `/C` (color, as the type defines it: for FreeText `/C` is the background, so text boxes get `/C []` and their text color in `/DA`), `/P` (page reference). Sticky notes and markup with a note get a linked `/Popup` annotation with the `/Parent` back-reference.
7. **Plain FreeText.** Use the base-14 Helvetica font through `/DA`, one font size and one color per box, plain-text `/Contents`, and an appearance stream. Do not write `/RC` rich text.
8. **Correct coordinates.** All conversions between screen and PDF user space go through `geometry.rs`, which handles `/Rotate` (0, 90, 180, 270), a CropBox whose origin is not (0, 0), and `/UserUnit`. Test each case with fixtures.
9. **Lean ink.** Simplify freehand strokes (Ramer–Douglas–Peucker, about 0.5 pt tolerance) before writing.
10. **Leave others' work alone.** Never rewrite, reorder or drop annotations the user did not touch. When the user edits an annotation made by another app, change only the edited keys plus its appearance, and keep unknown keys. Text markup whose QuadPoints are not in Acrobat order gets them put in it by that edit (the same corners), since the new appearance is drawn from them.

### 5.2 Reading other apps' annotations

- Display every standard annotation type MuPDF supports, including ones this app cannot create (shapes, stamps, links, file attachments).
- If an annotation lacks an appearance stream or has malformed quads, draw it for display from its properties, but write nothing. Mark it in the annotation list with a "needs repair" badge.
- QuadPoints out of Acrobat order need repair only when their corners are crossed (the spec's counter-clockwise order, a clockwise one), which readers that draw from them show as a bow-tie. Mirrored ones (the bottom edge first, as apps built on Apple's PDFKit write, or each edge from right to left) are the same shape read either way: with an appearance, the annotation shows correctly everywhere and nothing is reported (ADR 0017).
- Show replies (`/IRT`) in their parent's thread in the list. Replies Lectrix writes are notes linked by `/IRT` that nothing draws on the page: an empty appearance, a `/Rect` of no area at the parent's corner, no `/Popup` (ADR 0012; `docs/interop-profile.md`, "Replies"). Only their text and author change.

### 5.3 Repair annotations command

A command that scans the document, shows a summary of problems found (counts per problem type), and on confirmation fixes them in one undoable operation:

- generate missing appearance streams;
- reorder crossed QuadPoints into Acrobat order; mirrored ones stay as their app wrote them while the annotation keeps its appearance, and are put in order only where repair has to draw the annotation (ADR 0017);
- recompute `/Rect` where it does not contain the content;
- add missing `/NM`, `/F 4`, `/M`, and `/P`.

Repair must never change an annotation's content, color, author or position. Log every change to the app log with the annotation's object number.

### 5.4 Saving rules that protect interoperability

- Default save is incremental: changes are appended and the original bytes stay intact.
- If MuPDF reports the file was repaired on open (damaged cross-reference table), it cannot be saved incrementally; do a full save and tell the user once, in plain words, why. A file that opens without an error but with no pages (a cross-reference table that leads nowhere, such as a last section naming itself as the previous one) gets the same repair from Lectrix, and is then treated the same way; if it still has no pages, it is reported as too damaged to open.
- "Save As (optimized)" does a full rewrite with garbage collection and stream compression.
- If the document is digitally signed, warn before the first edit that edits will be shown as changes after signing, and always save incrementally.
- Encrypted documents: prompt for the password, keep the encryption on save, and respect permission flags (no annotating if the document disallows it).
- PDF/A: a file that claims a PDF/A level (`pdfaid:part` in the XMP metadata of the catalog's `/Metadata`; the claim is read, compliance is not checked) opens for reading only, as Acrobat opens it. The session refuses every operation meanwhile, the frontend offers nothing that changes the document (annotations, bookmarks, page labels, rotating, moving, deleting or inserting pages, repair; such a shortcut says why in a notification with an Enable editing button), and bookmarks expanded or collapsed meanwhile are not written. A banner under the view bar says so, with the level ("This file claims compliance with the PDF/A standard (PDF/A-1b), so it was opened for reading only. Saving annotations or inserted pages removes that claim."), and its **Enable editing** button makes the document one like any other for as long as it is open. Settings can open such files ready to edit (section 6.6), and one that comes with changes restored after a crash opens that way. Lectrix cannot vouch that what it writes complies, so a file never keeps a claim Lectrix may have broken: a save whose changes include an annotation added, changed, deleted or repaired, pages inserted from another file, or pages deleted, takes the identification properties (`pdfaid:part`, `conformance`, `amd`, `corr`, `rev`) out of the XMP, leaves the rest of the metadata as it was, and says so in a notification ("report.pdf no longer claims to be PDF/A-1b."). Changes undone before the save do not count. Bookmarks, page labels, page rotation and the order of the pages alone keep the claim, as does a Save As, optimized or not. A document restored after a crash loses the claim at its next save, since what its changes were is not known.

## 6. Feature specifications

Each feature below defines behavior. The "settled details" were decided during the v1 build; change them only with the user's agreement.

### 6.1 Viewer

- **Opening:** File > Open dialog, drag-and-drop onto the window, `.pdf` file association, and a path passed on the command line. Opening a file that is already open switches to its tab, in whichever window that is (it comes to the front). Lectrix is single-instance: a second launch hands its files to the window used last.
- **Tabs:** one tab per document, with a dirty marker (a dot; a spinning ring while saving) and a close prompt for unsaved changes. A document keeps its place while another tab, the Combine view or the start screen is on screen. A tab is reordered by dragging it along the row, where it follows the pointer and the others make way, or with Ctrl+Shift+Left/Right, and moves to another window when dragged off the row (section 8, Windows). Its context menu has Move to new window, Move to window (one item for each other window), Move left, Move right and Close.
- **Scrolling:** continuous vertical scroll, virtualized; only pages near the viewport are rendered.
- **Zoom:** fit width, fit page, preset percentages, Ctrl+wheel and pinch, centered on the cursor. Zooming glides to the new zoom in 140 ms: the + and − buttons and Ctrl+= / Ctrl+- (to the next preset, around the center of the view), the zoom menu, fit width, fit page (ending at the top of the current page) and mouse wheel notches (around the cursor). A step pressed during a glide goes on from where it was heading. A touchpad pinch follows the fingers instead, and re-fitting as the window or a pane changes size is immediate. Settings can turn gliding off, and reduced motion always does.
- **Navigation:** page box accepts a physical page number or a page label (typing `iv` jumps to the page labeled iv); a thumbnails panel; back/forward history for jumps (Alt+Left/Right).
- **Text:** selection and copy across lines and pages; a side of the selection (where it starts or where it ends) can be dragged to extend or reduce it, with handles drawn on the sides if Settings asks for them, and Shift with the arrow keys does the same from the keyboard; search with match highlighting and next/previous (Search, below).
- **Search** (Ctrl+F): a bar at the top right of the pages, which slides down 8 px into place as it fades in (140 ms) and goes the same way (100 ms), at once with reduced motion. It searches as you type, once typing has paused for 250 ms, without moving the view: the bar counts the matches ("52"), and Enter and Shift+Enter (F3, Shift+F3) go to the next and previous match, saying where it is ("3 of 52"). With none gone to yet, next is the first match from the current page on and previous the last one before it. Closing the bar keeps its text, which is searched again (the view left where it is) when the bar opens again. Under the field, a list suggests the words of the document that contain what is typed, as Acrobat's does: each word as the document spells it most often, with the number of matches a search for it finds, most first, at most eight, and not the word typed itself. A click, or the arrow keys and Enter, search for one and go to its first match from the current page on; Esc closes the list, then the bar. With text selected, Ctrl+F puts it in the field (on one line, at most 200 characters) and starts at the selection itself, unless the document forbids copying. While the bar is open, marks beside the pages' scrollbar show where the matches are in the document, the one shown taller and in a stronger colour; Settings can turn them off. Going to a match glides there in 140 ms, as a bookmark is glided to (Settings: "Smooth scrolling to search results", on by default; reduced motion turns it off).
- **Links:** a link in the text is followed with the Select tool: the pointer shows the hand over it, its area is tinted meanwhile (the link's `/Rect`, in Lectrix blue at 16%), a tooltip says where it leads, and a click follows it. The tooltip is the comment tooltip of section 6.5 (the same look, place and delay): "Page 176" for a place in the document, naming the page as the page box does (its label, else its number), the address for a web or other address (cut at 160 characters), and what it is for the rest ("Another file: appendix.pdf", "JavaScript action, which Lectrix doesn’t run", "Leads nowhere in this document"). Settings can turn off the tint and the tooltip, each by itself. A place in the document (a line of a table of contents, a cross-reference) is gone to as a bookmark's is (gliding there, section 6.2), recorded in back/forward history, so Alt+Left returns. A web address (http or https) opens in the system's default browser, and a notification says which address that was ("Opened in your browser", then the address). Rust opens it (`open_link`), and only an address that a link on that page of the document carries (for a bookmark: that bookmark), so the webview can have no other page opened, and nothing but a web address is ever handed to the system. Any other address (mail, a file), another file or an action is described in a notification (an address with Copy link), never opened or run. Bookmarks are followed the same way (section 6.2). A drag that starts on a link selects its text and follows nothing, and an annotation or a side of the selected text comes before a link under it; the other tools leave links alone.
- **Scroll modes** (View > Page display, and a button in the view bar whose icon shows the mode in use): single page, single page continuous (the default), two pages and two pages continuous, plus "Cover page alone" for the two-page modes (the first page on its own, on the right, as a book's cover). A document opens in the mode Settings chooses: one of the four, or "As the document asks", its `/PageLayout` (single page continuous when it asks for none; the `…Right` layouts turn the cover on). The mode belongs to the tab and is not written to the file.
- **View rotation:** rotating the view (View > Rotate view) turns every page as it is shown and does not modify the document. One page can be turned by itself, on top of that: the Pages panel's rotate buttons turn the current page, and a thumbnail's context menu turns its page. That is on screen only too, never written to the file: nothing to save or undo, and a file open for reading only has it. The view rotation and each page's turn are remembered for the file with its view position, in app data. Pages are rotated in the document (`/Rotate`, undoable) in the page organizing tool (section 6.7), and only there.
- **Full screen** (View > Full screen, F11): the window fills the screen and shows the pages alone. The title bar, the view bar and the side panes slide out of the window (140 ms, at once with reduced motion) over the pages, which have all of it at once, and the window fills the screen as the last of them goes. Leaving is the same the other way round: they slide back in over the pages, and the window returns as they arrive. It ends with F11 again, with Esc once nothing else is left for it to step back from, or with the Leave full screen button at the end of the toolbar. Meanwhile the annotation toolbar floats, whatever Settings say of its placement, at the edge and with the visibility Settings give the floating toolbar (section 6.6), and holds the page and zoom controls before the tools. At the left or the right of the screen all of them are stacked, as the tools are there in a window (section 8): previous and next page, the page box with the position under it in small text ("of 312", or "(4 of 312)" on two lines), zoom out, the zoom level, zoom in, the page display and the visual adjustments, whose menus and panel open beside the toolbar. The pointer at the left or right side of the screen brings that side's pane, which lies over the pages (they keep their size) and goes once the pointer has left it. Alt held down shows both panes at once, and the toolbar when it shows only near its edge.
- **Visual adjustments** (a button among the page and zoom controls, after the page display, with a dot on it while anything is adjusted): a panel with Brightness and Contrast (sliders, 50% to 150% in steps of 5, 100% as the pages are), Sepia (a slider, 0% to 100% in steps of 5, 0% as the pages are: an e-book's sepia, which gives the paper the tone of old paper, the more the further, and leaves black text black), Invert colours and Greyscale (switches), and Reset. They apply at once, to the document's pages and to its thumbnails in the Pages panel, and to nothing else in the app. They are how the pages are shown, never a change to the file: nothing to save or undo, and a file open for reading only has them too. A document is shown with the adjustments Settings give every document (section 6.6: the pages as they are, until changed there), and follows them as they change. Changed in the panel, it has adjustments of its own from what it showed, remembered for its file with its view position, in app data; Reset takes them away again, and it follows Settings as before. The dot is there while the pages are not as the file has them, whichever of the two adjusts them.
- **Pages panel toolbar:** under the panel's title, rotate the current page counter-clockwise or clockwise (as it is shown, never in the document: see View rotation; the page's context menu in the viewer has no rotation, the thumbnail's does), make thumbnails smaller or larger (64 to 456 px wide, never wider than the panel), fit them to the panel's width (a toggle; they follow the width as the pane is resized, until Smaller or Larger is pressed), and switch between one column and a grid of as many columns as fit (one button whose icon shows the layout in use; arrow keys move across and down the grid). A size from these buttons glides there in 140 ms, as zooming does (off with smooth zooming, or reduced motion); resizing the pane follows it at once. The size, the fit and the layout are remembered in app data with the panes.
- **Start screen** (no document open): the app's icon and name, then the tools (Open…, Combine files…, Organize pages…) as tiles in a grid with room for more, then the recent files. Organize pages… asks for a file, as Open… does, and shows its pages as a grid to organize (section 6.7); a file that is open already is organized in its tab. At rest a tile is plain: a border in the line's colour (two device pixels at any display scale), its icon and text in the text's colour. Under the pointer its border, icon and text take one brand gradient laid across the whole grid (deepened in the light theme so its text reads at 4.5:1), and a wash of it fills the tile; it glides there and back in 120 ms. With documents (or the Combine view) open, the app's icon and name in the title bar show the start screen over them: nothing closes, the tabs stay with none of them selected, and the same click, a tab or Ctrl+Tab goes back (Ctrl+Tab to the document it was shown over). Opening a file from there, or a recent file that is open already, goes to its tab; a tab closed from there leaves the start screen showing, unless it has changes to ask about.
- **Recent files** list and remembered per-file view position (page and zoom), view rotation, pages turned on screen and the document's own visual adjustments, stored in app data, not in the PDF. The start screen shows the list newest first, as a table or a grid (two buttons beside the "Recent files" heading switch between them, the mark of the one shown gliding to the one picked as the active tool's does; the choice is remembered in app data with the panes). Switching brings the files in animated: each rises into place as it fades in, the first few a moment apart, 140 ms in all (at once with reduced motion); they are not animated when the start screen first shows them. The table has the name with Lectrix's PDF file icon (the folder in its tooltip), when it was last opened ("Today, 19:07", "Yesterday, 22:16", then the day and month, and the year before this one; the hour unpadded, in the system's 12- or 24-hour style) and the size as File Explorer counts it. The grid shows each file's first page, with its annotations, in a page-shaped area, and under it the name, then the date and size ("Today, 19:07 · 1.5 MB"); a file that is missing, needs a password or cannot be read shows the file icon instead. A click on a row or card opens the file; a button on it, shown on hover or focus, removes it from the list.

Settled details:

- Single page and two pages show one row at a time. Scrolling, Page Down, the down arrow or Space past its end shows the next row from its top; the same back past its start shows the previous one from its bottom. A mouse wheel notch at the edge turns at once; a touchpad turns once it has gone a notch past the edge, and once per gesture. Left and Right turn when the row is no wider than the view; Home and End go to the first and last row. Turning is not recorded in back/forward history.
- In the two-page modes, pages of a row meet at the middle of the view, a page alone keeps its side (a cover on the right, a last page on the left), and pages of different heights are centred on each other. The current page is the row's first; previous and next page turn a row; fit width and fit page fit the row's two pages. Changing the mode keeps the current page and refits a fitted zoom.
- The view bar's Previous page and Next page buttons glide to the page in 140 ms, as the view glides to an annotation picked in the list (section 6.5). Pressed again meanwhile, they go on from the page the glide was heading to; scrolling or clicking stops the glide. In single page and two pages there is nothing to glide over, so the row turned to comes in instead: it rises 24 px into place as it fades in, or comes down for the row before. Settings can turn this off ("Smooth scrolling to the next and previous page", on by default), and reduced motion always does. Rows turned by scrolling or with the keys are not animated.
- Fit width and fit page use the current page when applied, and re-fit only when the window size or the view rotation changes or a page is turned on screen, not while scrolling past pages of other sizes.
- A page turned on screen is laid out on its side or upside down, with the pixels it has (they are turned with the page, not rendered again for the turn). The view stays on the current page. Text selection, links, search hits and annotations are where the page shows them, as with a rotated view, and new annotations are placed upright as seen there (section 6.5). Its thumbnail shows it turned too; thumbnails do not follow the view rotation. A turn belongs to its page: it follows the page when pages are moved, deleted or inserted (section 6.7). The grid of pages being organized, the start screen's previews and the Combine view show pages as the file has them.
- Search is case-insensitive, starts at the current page and wraps. Search jumps are not recorded in back/forward history; page-box and thumbnail jumps are.
- A suggestion's words are found within a line (`words_containing` in `text.rs`, in the same pass as the matches): each match of the query taken out to the word boundaries on both sides (letters, digits, combining marks, an apostrophe between two of them), with spaces in the query matching a run of them, so a query of two words suggests the words around them too. They are gathered case-insensitively (`FoundWords` in `viewer/suggestions.ts`). A suggestion's count is what a search for it finds, so it counts the longer words it is part of ("lecture" counts "lectures"); a match that runs from one line onto the next is not counted, which can leave a suggestion a match or two short of its search. The list waits while typing has not yet started a search for the field's text, rather than show another query's words.
- After an edit, the search runs again and the match shown stays the one shown (the first from its page on), without moving the view (`SearchState.refresh`). Enter or a match button pressed before the search has reached the pages it needs goes there once it has.
- A search started from selected text shows first the match whose first line holds the selection's first character (`firstHit` in `doc.svelte.ts`); with none there, the first match from that page on.
- The marks stand for the whole document laid out end to end (`searchMarks` in `viewer/searchmarks.ts`), where the scrollbar shows them when all the pages scroll; in single page and two pages they still stand for the whole document. One mark per pixel row, over the scrollbar's track, which they let the pointer through to. In single page and two pages, a match in another row has that row come in, as a row turned to does.
- Copying respects the document's copy permission.
- A double-click selects the word under the pointer, a triple-click its line; a drag that goes on from either keeps the word or line whole and selects on from it by whole words (or whole lines): the word the pointer is in is selected whole, as in a word processor (`extendByUnit` in `viewer/selection.ts`).
- The sides of a text selection are the start of its first line and the end of its last. Within 5 px of one, the pointer shows the resize arrows along the line; a drag from there moves that side while the other stays, and past the other side the selection turns over. Nothing is drawn on the sides unless Settings' "Show handles on selected text" is on: then each side has a bar the height of its line with a knob, at the top of the start and at the bottom of the end, the same size at any zoom and in one blue in both themes (the page is white in both); the handles change nothing else. A side pressed and let go changes nothing; a double-click there still selects a word, and Shift+click extends as before. A side comes before an annotation under it. With a markup tool, the changed selection is marked on release, as any selection is.
- With text selected and the page in focus, Shift and an arrow key move the end of the selection (the side last dragged or moved by the keys; after a plain drag, where it was let go) while the other side stays: Left and Right by a character, Up and Down by a line (keeping its place across shorter lines), and with Ctrl too, Right to the end of the word and Left to the start of one, Down to the end of the paragraph and Up to its start, then the next one's. Left and Right follow the text's reading order. The keys cross lines and pages (pages without text are passed), never leave nothing selected (a step that would end on the other side goes on past it, and the selection turns over), and scroll just far enough to keep the moving end in view. Without a selection or a text cursor the keys scroll as before; a selection is started from the keyboard only from the text cursor.
- A click in the text with the Select tool or a markup tool puts a text cursor there (`DocTab.caret`): a 1.5 px black line (`--lectrix-text-caret`; the page is white in both themes) as high as the character beside it, blinking as Windows' cursor does (530 ms on, 530 off; steady with reduced motion) and shown only while the pages have the keyboard focus. Left and Right move it by a character, Up and Down by a line, with Ctrl by a word and a paragraph, as Shift with them moves the end of a selection, except that the end of a line and the start of the next are two places for it; meanwhile they don't scroll or turn rows (Page Up, Page Down, Home and End still do). Shift with them selects from it, and the selection then goes on as one made with the pointer: with the Select tool the quick tools come, with a markup tool it is marked (section 6.5). A click that follows a link or selects an annotation puts no cursor; a click elsewhere, Esc, the other tools (pen, note, text box), a selection with the pointer or any change to the document takes it away. Switching between Select and a markup tool keeps it.
- Full screen comes and goes in two steps (`Stage` in `fullscreen/fullscreen.svelte.ts`): the slide, then the window. In that order because switching the window makes the webview lay out and draw everything again at the new size, which holds its frames up for 40 to 100 ms (most the first time): a slide started with the switch was lost in that, and one that waits for it starts 150 ms after the key. During the slide the bars and panes are laid out as in a window, and the pages have the whole window or screen under them (`viewer-covers`), so no gap opens where a bar was. They move by transforms and opacity alone, which the compositor does without laying anything out. The window is asked to switch just before the slide ends (50 ms going in, 20 ms coming back, the time it takes to answer), and in the frame that brings its new size everything is laid out for it, once. The toolbar is full screen's own from the start of the slide in to the start of the slide out, and the notification that says how to leave goes when leaving.
- Full screen starts only with a document on screen, and ends by itself when none is (the last tab closed, the Combine view shown); switching tabs keeps it. It belongs to its window and is not remembered: a window closed full screen comes back at the place it had before. The first time it starts while Lectrix runs, a notification says how to leave it and how to reach the panes. A file open for reading only shows no PDF/A banner meanwhile (a change tried there still says why not, with Enable editing); the banner of a file changed on disk shows.
- Full screen, the pointer brings a pane once it has rested for 150 ms within 4 px of that side of the screen with no button down, so a drag never brings one and the pages' scrollbar beside it stays usable. The pane goes 300 ms after the pointer has left it, but not during a drag (its edge being resized), while the pointer is on a menu, or while text is typed in the pane. A pane a command asks for (the panel and pane commands, Ctrl+B) shows until it is hidden again or the page is pressed. The pane's button, in its row, hides it, and the pointer must then leave that side before it brings the pane again. The panes the window had open are kept for when full screen ends, and nothing done meanwhile changes them.
- Alt counts as held after 150 ms by itself: with another key it is that shortcut's Alt (Alt+Left) and shows nothing. Pressing the page ends what Alt shows (an area highlight is drawn with Alt held), and letting Alt go keeps the pane the pointer is on. Full screen, Alt by itself does not reach the system, which would open the window's menu. A toolbar that shows only near its edge also shows for 1.5 s as full screen starts.
- Visual adjustments are a CSS filter on each page's layer (`pageFilter` in `viewer/adjustments.ts`): its pixels and what is drawn over them (the selection, search hits, a text box being typed), so what shows on a page stays as visible as it was. The page's shadow, and the bars and panels over the pages, are outside it. Greyscale comes first, then the inversion, then brightness and contrast, which so act on what is seen (less brightness dims an inverted page's light text). Sepia is not in the filter: CSS's `sepia()` leaves white paper nearly white and takes the colours away. It is the tone of old paper (`--lectrix-sepia-paper`, `#F0E0BD`) laid over the page and multiplied into it (`.page-tone`, `pageTone`), as much of it as the slider says: white paper takes the tone, black stays black, pictures keep their colours, warmed. It lies over the filtered page, so it tones what is seen: an inverted page keeps its dark paper and has its light text warmed, and more brightness does not wash the tone out. A document's own adjustments are `DocTab.ownAdjustments` (null while it follows Settings) and `ViewState.own_adjustments`; a view stored up to 1.1, which had adjustments whether anything was adjusted or not, gives the document its own only if something was. A change that leaves a document looking as Settings say takes its own away. After Reset the keyboard focus goes to the first slider, since the button is disabled then. Invert colours inverts lightness and keeps hues (`invert(1) hue-rotate(180deg)`): a yellow highlight stays yellow on the dark page. An inverted page waits dark for its pixels. Rust renders the pages as they are, and its image cache knows nothing of this. The panel opens with a click or Enter; Esc closes it and nothing else. The start screen's previews and the Combine view show pages as they are.

### 6.2 Bookmarks (outline)

- A panel (section 8) with the outline as a tree. Expanded/collapsed state is read from and written to the outline.
- **Add bookmark** (Ctrl+B) at the current page and scroll position; if text is selected, use it as the title.
- **Edit:** rename inline (F2 or double-click), drag to reorder and nest, delete (with children, after confirmation), "Set destination to current view."
- New and retargeted bookmarks get explicit destinations: page reference, `/XYZ`, left and top of the current view, null zoom (keeps the reader's zoom).
- Existing bookmarks the user did not edit keep their original destination or action exactly, including named destinations and URI actions.
- Titles with non-ASCII characters are written as UTF-16BE with a byte-order mark.
- Titles are shown as Acrobat shows them: up to their first NUL character (some producers pad titles with them), with other control characters, such as a line break at the end, as spaces, and without spaces at the ends. The title in the file stays as it is until the bookmark is renamed.

Settled details:

- A click selects a bookmark and follows it; arrow keys only move the selection; Enter follows. The selection stays when the page is clicked, so repeated Ctrl+B builds a list in order.
- Following a bookmark glides the view to its place in 140 ms (Settings: "Smooth scrolling to bookmarks and links", on by default; reduced motion turns it off). A long way starts one screen from the place, where its page is in view from the first frame, so the pages passed are not rendered first. In single page and two pages, a bookmark in another row has that row come in as a row turned to does (section 6.1). Scrolling or clicking stops the glide. A link in the text that leads to a place in the document is glided to the same way, under the same setting.
- Ctrl+B puts the new bookmark right after the selected one, as its sibling; with nothing selected, at the top level, in page order. Without selected text it is titled "Page <label>" and opens for renaming. Selected text is used only if the document allows copying.
- A new or retargeted bookmark points at the top-left of what is visible on the page at the top of the view (in the page's own orientation), rounded to whole points.
- Deleting a bookmark without children needs no confirmation (it can be undone).
- Expanding or collapsing is not an edit: it neither dirties the document nor adds an undo step, and is written at the next save. It is not written for a signed document without other changes, or when permissions forbid outline changes.
- Bookmarks untouched by an edit keep their bytes exactly; neighbours whose links change are rewritten by MuPDF with the same destination and action values.
- A bookmark that is a web link (http or https) opens in the system's default browser when followed, as a link in the text does (section 6.1), with the same notification; its inspector has Open in browser beside Copy link. Other addresses, other files and actions are described in a notice when clicked, never opened or run. A bookmark's own color shows as a dot, not as text color.
- The inspector opens from the context menu (Properties), then follows the selection until closed. It floats over the page, so it never changes a fit-width zoom.

### 6.3 Page labels

- Set in a dialog over the grid of the page organizing tool (section 6.7), as Acrobat's Page Numbering is, and offered only there: the tool's bar has a **Labels** button for it, and the grid's menu has **Page labels…**. While a document is read, no menu has page labels, neither the Document menu nor a page's in the Pages panel. The command ("Page labels, while organizing pages" in Settings > Shortcuts, without a default shortcut) opens the dialog in the grid and does nothing while reading.
- **Pages:** all of them ("All 212 pages"), the pages selected in the grid ("Selected: 3 pages (5–7)"), or from one page to another, by their places in the document. With pages selected the dialog starts with those; with none, Selected is disabled and it starts with the range, set to the page with the keyboard focus in the grid (the page the document was at, until another is picked).
- **Numbering:** **Start a new section**, with a style (1 2 3, i ii iii, I II III, a b c, A B C, none), an optional prefix and a first number (1 or higher), or **Continue the numbering of the page before**, which is how a range is taken away again.
- **Apply** numbers the picked pages, in one undo step; every other page keeps the label it has. Cancel, Esc or closing the dialog changes nothing.
- **Live preview:** while the dialog is open, the labels under the grid's pages show what Apply would give, and a line of the dialog says it in words ("Preview: i, ii, iii … xii").
- Letter styles follow the PDF convention: a…z, then aa…zz, then aaa…zzz.
- Opening a file shows its existing labels exactly as stored; saving writes the `/PageLabels` number tree in the document catalog, with a rule at the first page, which the format requires.

Settled details:

- A new section starts as "1, 2, 3 from 1" each time the dialog opens, like Acrobat's "Begin new section", whatever the pages have now.
- Pages that are not next to each other are numbered through, in page order (pages 2, 3 and 7 become i, ii, iii), and the pages between them keep their labels.
- The pages after the picked ones keep their labels: a rule at the first of them says what it had (`assignLabels` in `labels/rules.ts`). Rules that start inside the picked pages go. A rule this would add that only repeats the rule before it is not written.
- Continue the numbering is disabled while the first page of the document is among the pages: it has no page before it.
- A document numbered 1, 2, 3 throughout by a change is left without `/PageLabels`: all pages as "1, 2, 3 from 1" removes all labels.
- Cancel leaves the grid as it was. After Apply to all pages or to a range, the first numbered page comes into view. Versions up to 1.1 had **Document > Page labels** and **New label range from this page**, in the Document menu and in the Pages panel's; a shortcut stored for the second is ignored.
- Versions up to 1.1 had the labels in a side panel of their own. A pane layout remembered from then loads without that panel.
- An invalid value says why under the fields ("Enter pages between 1 and 8, the first no later than the last.", "Numbers start at 1 or higher."), and Apply is disabled meanwhile.
- Stored rules that start after the last page have no effect, and the next change removes them. A file without a rule at page 1 is numbered 1, 2, 3 from there.
- A page whose label is empty (a range with the style "None" and no prefix) has no label, and is not given its page number in its place: the page box is empty there, with the physical position after it ("(4 of 312)"), and the thumbnail has no caption. The page number typed in the page box still goes there. Where a sentence names the page ("Page 4": a link's tooltip, the annotation list's headings, a new bookmark's title, accessible names), it is named by its number. A document without `/PageLabels` shows page numbers throughout, as before.
- A document without labels gets no `/PageLabels` tree until something is changed.
- Changing labels needs the same permission as rotating pages; in a signed document, the first change shows the signed-document warning. Where labels can't be changed (permissions, or a file open for reading only), the bar's button and the grid's menu item are disabled.

### 6.4 Stitching (combine files)

- A Combine view: add files (dialog or drag-and-drop), see them listed in a pane at the left and all their pages as thumbnails in one grid, and reorder, remove or rotate pages before combining.
- **Bookmark option** (default first): nest each source's outline under a new top-level bookmark named after the source's title or file name; or keep outlines flat; or drop them.
- **Page label option:** keep each source's labels (default); one continuous decimal sequence; or no labels.
- Annotations travel with their pages and still pass the interop profile afterwards.
- Internal links and named destinations are remapped to the new pages; colliding destination names and form field names are renamed with a per-source prefix, and the user is told how many were renamed.
- The result is always written to a new file via Save As. Source files are never modified.
- Also expose "Insert pages from file" into an open document, using the same engine.

Settled details:

- In the grid (`PageGrid.svelte`, shared with the page organizing tool), a click selects a page, Ctrl+click adds or removes one and Shift+click extends the selection. A page is dragged by its picture, and the selected pages go with it. A drag that starts anywhere else (a caption, the space between pages) draws a rectangle, which selects the pages whose pictures it touches as it grows: in place of the selection, or added to it with Ctrl or Shift held. Esc during a drag or a rectangle leaves everything as it was. A click on a caption selects its page. A selected page has a tint and a border around its whole block (its picture and what is under it), and the page with the keyboard focus a ring around that: in the accent in the page organizing tool, and in the colour of the page's file in the Combine view (`--page-cell-accent`). The columns are centered in the view, and so is a single row of fewer pages than fit.
- Under a page is its label alone (its place in its file after it where that says something else, "iv (4)"), not its file's name: the file is told by the colour a selected page has, and named in the page's accessible name. The page under the pointer tells it too: its block has a lighter tint of its file's colour and a thin edge in it, and a tooltip under the block names the file. Under the pointer, the label gives way to a bar in its place, centered under the picture: the same label, then buttons that turn that page counter-clockwise and clockwise and remove it. The bar has the measures of the bars that float over a page (an annotation's): their edge and shadow, and 32 px buttons with 16 px icons; the label's line is as tall as the bar (36 px), and 8 px of the block are under it, so the bar does not sit on the block's edge.
- The files and the options are in a pane at the left, which resizes from its inner edge as a side pane does (section 8): 180 to 480 px, 224 px at first and after a double-click on the edge, at most 40% of the window. Its width is remembered in app data with the panes.
- The list shows each file with its colour (six of them, in turn, as the files are added: `--lectrix-source-N`), its name and how many of its pages are in the result. A file is dragged up or down the list to another place: its name follows the pointer, a line shows where it would go, and Esc leaves it where it was. Alt+Shift+Up/Down do the same from the keyboard for the file with the focus, and Up and Down move between the files. Its pages go with it (`gatherPages` in `merge/pages.ts`): they come together, in the order they have, before the first page of the file listed after it (the next one with pages in the result; at the end without one), and the other pages stay as they are. One undo step, which puts the list back too. Dragging pages in the grid leaves the list as it is.
- The pictures change size as in the page organizing tool (section 6.7, `GridZoom`): the toolbar's Smaller pages and Larger pages buttons, Ctrl+= and Ctrl+-, Ctrl and the mouse wheel, and a touchpad pinch; the same sizes (160 px at first, up to one page filling the view), gliding the same way. The size is kept while the Combine view is open, and not remembered after.
- The Combine view is a tab of its own. Closing it asks first if pages were arranged but not combined. The result opens in a new tab, and the Combine tab stays open.
- Combining reads files as saved on disk. If one is open with unsaved changes, Lectrix offers "Save and combine", "Use saved version" or "Cancel".
- Files that forbid copying content are not added, with a plain message. Encrypted files that allow it ask for their password; the combined file is not encrypted.
- Before combining signed files, or inserting pages from one, Lectrix warns that the signature will not be valid in the result ("Combine anyway" / "Insert anyway", or Cancel). Signature fields are copied as they are.
- The same file can be added twice. Renamed names get a prefix by source position, the file's place in the list among the files with pages in the result ("src2_chap2"), or "inserted_" when inserting, plus a number if that is taken too.
- Top-level bookmarks follow the order of each file's first page in the result. "Each page keeps its label" numbers unlabeled files 1, 2, 3… from their first page; when the result would be 1, 2, 3… throughout, no `/PageLabels` is written.
- Insert pages: the pages go into the grid of the page organizing tool (section 6.7), which **Document > Insert pages from file…** shows first if it is not on screen. There they go after the page the document is at, or where the grid says (after the selected pages, at the place its menu names, into the gap a file is dropped on). The dialog asks which pages of the file and what happens to its bookmarks and page labels, and says where the pages go ("Into report.pdf, after page iv."); it does not ask where. Several files can be picked, or dropped, at once: the dialog then lists them with their page counts ("Insert pages from 3 files") and asks nothing about pages, since every page of each goes in, in the files' order, one after another. Each file is one undo step. A file's bookmark goes among the top-level bookmarks in page order.
- Not carried over: the structure tree, article threads, document-level JavaScript, open actions, viewer preferences and XMP metadata. The combined file is a plain full save.

### 6.5 Annotations (user interface)

- **Toolbar tools:** Select, Highlight, Underline, Strikeout, Squiggly, Note, Pen, Text box.
- **Text markup:** with a markup tool active, selecting text creates the annotation on mouse-up. A click in the text puts a blinking text cursor there (section 6.1); Shift with the arrow keys selects from it, and letting Shift go creates the annotation. Alt-drag creates an area highlight (one rectangular quad) for scanned pages without text. New text markup (from a tool, the quick tools or Alt-drag) is not selected, unless Settings' "Add a comment after marking text" is on: then it is selected and the cursor goes in its note, in the inspector, or in its row of the annotation list while the list shows it.
- **Quick tools:** with the Select tool, selected text gets a floating bar above the point where the pointer was released (below it when there is no room above; released on the last selected line, the bar keeps clear of that line), with the colour button first (the colour every tool draws with, so it can be picked before the text is marked; its panel has no opacity, which is each tool's own), then the tools chosen in Settings: Highlight, Underline, Strikeout, Squiggly, Highlight with note, Copy, Add bookmark. Picking a colour there leaves the selection and the bar.
- **Select tool on annotations:** a click on an annotation selects it as an object. A drag that starts on one that doesn't move (text markup, and shapes, stamps and others Lectrix can't move) and over text selects that text instead, as a drag anywhere else does; notes, drawings and text boxes are moved by a drag.
- **Annotation bar:** clicking an annotation without a comment selects it and shows a floating bar above it: color, type (text markup only: highlight, underline, strikeout, squiggly), note, delete. Clicking an annotation with a comment (not a text box, whose text is on the page) shows its inspector instead, with the bar's controls in its header. Double-clicking puts the cursor in the inspector's note; while the annotation list shows the annotation, at the end of its comment in the list instead.
- **Style:** one color for every tool, which new annotations get whatever the tool, and an opacity, a stroke width (pen) and a font size (text box) for each tool. The toolbar's color button is always there, before the tools, so a color can be picked before a tool is; its panel has the opacity of the active tool, and none with the Select tool. The number keys 1 to 9 pick the first nine presets as that color (commands with shortcuts, Settings > Shortcuts), and never recolor a selected annotation. 18 preset colors (Acrobat's until changed in Settings, section 6.6, and the same for every tool; three rows of six, 6 px apart: bright colors, yellow, green, red and blue first, then orange and purple, their light tints under them, white to black; arrow keys move among them) plus a custom color and opacity (a slider, 10% to 100%), in one panel that a button showing the color in use opens, as Acrobat's picker does; the same in the toolbar, the annotation bar, the inspector and the annotation list's selected row. The panel opens when the pointer has rested on the button for 150 ms (Settings can turn this off), and on a click or Enter. Opened by the pointer, it takes no focus and goes 300 ms after the pointer has left the button and the panel; once something in it is pressed or focused, or the button clicked, it stays until Esc or a click elsewhere, as a panel opened by a click does. Under the presets is the opacity slider with its value and, at the end of that row, the custom color's button, which slides Lectrix's own picker open below (140 ms, at once with reduced motion; open from the start when the color in use is not a preset): a saturation and brightness square, a hue bar, the eyedropper, and a field that takes a hex value only (six or three digits, no RGB or HSL). A color applies when picked (from the picker: when the pointer is let go, on Enter or leaving the field, or half a second after the arrow keys stop) and the panel stays open for the opacity, which applies when the slider is let go, stroke width for the pen; the color and each tool's last-used style are remembered, including a color given to an existing annotation, which new annotations then get, and an opacity, which new ones of its type then get (Settings can turn this off: new annotations then start from the defaults each time Lectrix starts). Until changed, the color is Acrobat's highlight yellow (`#FFD100`, the first preset), highlights have Acrobat's 40% opacity and the other tools draw opaque. Versions up to 1.2 kept a color for each tool: the highlight's became the one color, and presets changed in Settings kept their colors in the new order.
- **Inspector panel** (the comment panel) for the selected annotation: a header with the bar's controls (color, stroke width or font size, type, Properties where the bar has it, and delete at the right end), then note text, replies and repair. It sits beside the annotation (right, else left, else below), scrolls with the page, and a tail with curved sides points at the annotation's centre: from the side facing it, opposite that centre, or out of a corner when the centre is off that corner. It drags from anywhere but its controls, within the visible part of the view, and resizes from every edge and corner. Where it was put and the size it was given are kept for each annotation while the app runs. Other annotations' inspectors take the last size given as a limit: its width, and no more height than their content needs. While the annotation list is on screen and has a row for the selected annotation, the page shows neither its inspector nor its bar: the row stands in for both, with their controls above the comment. A reply shown in a thread has no row, so it gets its inspector or its bar.
- **Properties dialog** for the selected annotation, from Properties in the page's context menu (or the bar of an annotation Lectrix can't change): the author, changed with Save (one undo step), and the creation and modification dates.
- **Annotation list** in the right pane by default (section 8): click to jump, edit note text, delete, "needs repair" badges. Its header shows how many annotations the document has ("5 of 12 annotations" while some are hidden) and three buttons. **Search** opens a field (sliding open, as the filters do) that filters the rows as you type (once typing has paused for 200 ms, so the rows and the pages are not worked out again for every key; an emptied field applies at once), by their comments and replies, or, with the switch in the field, by the text they mark (text markup only; each page's text is read the first time). Esc empties the field, then closes it. **Sort** orders the rows by page (the default), author, date created or date modified, A–Z (first page, A, oldest first; the default) or Z–A, the order kept when the sort changes; rows without an author or a date go last either way. The rows of a page go as they appear on it, not as they were made: top to bottom, and left to right among those that start on the same line (text markup starts where its text does). They show under headings of the page, the author or the day. **Filter** opens a panel below the header with the types present as their icons, the colours present as swatches and the authors as pills, each under its subheading (Type, Colour, Author); picking several in one row shows any of them, and the rows combine. A dot on the button marks picked filters; Clear filters empties them. Each row shows the type as an icon in the annotation's colour, moved toward the text colour only as far as 3:1 contrast on the pane needs (its name as tooltip and accessible name), then the author and a short date, then the whole comment with its line breaks. Each page's group starts with a header under a dividing line. A right-click (or Shift+F10) offers Reply, Copy comment and Delete annotation; on a reply in a thread, Edit reply, Copy comment and Delete reply.
- Annotations can be moved, resized (ink, text box, notes) and deleted; every change is undoable.
- Author name is set in Settings, defaulting to the Windows user name.

Settled details:

- With the Select tool, a press on an annotation that doesn't move, over text, waits: let go within 3 px of where it was pressed, it is a click and selects the annotation; moved further, the annotation is not selected and the text is, from the press (the `press` gesture in `Viewer.svelte`). A press away from text, a double-click, Shift and the corner handles act at once, as before.
- With a markup tool, text selected from the text cursor (section 6.1) is marked when Shift is let go, as a drag is when the pointer is: with that tool, in its last-used style. The cursor then stays at the end the keys moved, so they can go on (unless the new markup opened its comment, Settings). A selection made by the keys with the Select tool is not marked by picking a markup tool afterwards.
- The quick tools' markup uses each tool's last-used style; "Highlight with note" makes a highlight and puts the cursor in its note (in the inspector, or in the annotation list while that shows it); "Add bookmark" does what Ctrl+B does. Tools the document forbids are shown disabled; with none allowed or none chosen, no bar appears. The default set is Highlight, Underline, Strikeout, Highlight with note and Copy.
- Each selected annotation shows either its inspector or its bar: the inspector if it had a comment when selected (it stays while the comment is edited, even emptied), or when opened from the bar, a double-click or the annotation list; otherwise the bar. Selecting another annotation decides again for that one. The inspector closes with Esc (from a control other than the note), and the bar takes its place until the annotation is clicked again, or when nothing is selected. While the annotation list shows the annotation, its row has both, and the page neither.
- Changing an annotation's type keeps its quads, color, opacity, note and author (one undo step, "Change highlight to underline"). The bar of a text box edits its text in place, as a double-click does; an annotation Lectrix can't change gets a Properties button instead.
- Notes are placed with one click; the inspector opens focused on the note field (while the annotation list shows the note, the cursor goes in its row's comment instead). Text boxes are typed in place; Ctrl+Enter or a click outside finishes, Esc discards. An empty new box is not created; emptying an existing one deletes it (one undo step).
- The inspector's color for a text box is its text color (rule 6 in section 5.1).
- Deleting an annotation that has replies asks first, then deletes the replies and the popup with it.
- A text box from another app that has a callout line can be edited but not moved or resized.
- The list shows markup, notes, drawings, text boxes, shapes, stamps and attachments; popups, links and form widgets are not listed.
- Reply opens a field under the thread; Ctrl+Enter or leaving it sends, Esc drops it, and an empty reply is not written. Edit reply edits in place the same way; emptying a reply deletes it. Replies are written only to annotations in the list's rows, not to replies, as Acrobat's list does; each is one undo step ("Add reply", "Edit reply", "Delete reply").
- While the list is on screen, the annotations its search or filters leave out are hidden on the page too: not drawn there (the page image is asked for without them), and not found by the pointer. Replies go with their thread. Thumbnails keep showing every annotation, and so does the page once the list is closed or another panel shows in its place. Nothing vanishes under the user's hands: the selected annotation keeps its row and stays on the page though a change (its colour, its type, its comment) made it stop matching, until it is deselected; another search or other filters deselect an annotation they leave out; and an annotation that has just appeared (made, or brought back by undo) clears a search and filters that would leave it out.
- The list's date is the last change, as Acrobat shortens it: the time for today, day and month this year, with the year before that; the full date and time are in its tooltip and in the Properties dialog.
- The list's order on a page is by position alone: annotations start on the same line when their tops are no further apart than half the height of the shorter one (for text markup, its first line). Text in columns is not followed: a mark at the top of the second column comes before one lower in the first. Z–A by page shows the last page first, each page still from its top. Rows that another sort can't tell apart (one author, the same time) go in page order, then by position.
- A selected row stands in for the annotation's inspector and bar, which the page doesn't show meanwhile. Above its comment it has the inspector's controls (color, stroke width or font size, type, Properties where the inspector has it, and delete at the right end), and it edits its comment in place in a field as tall as the text, at the same text size. It comes into view when the annotation is selected on the page. What would put the cursor in the inspector's note puts it at the end of the row's comment: a double-click on the annotation, a new note, new text markup that opens its comment, "Highlight with note". Up, Down and Delete pressed on the row's controls are theirs: they neither move the selection nor delete the annotation. A comment shown as text is inset as the field that edits it, so it stays where it is when its row is selected, and the row's first line (type, author, date) starts at the same inset.
- A comment typed in the inspector's note or in the selected row's field is written when the field is left, however that happens: a click anywhere (on the page too, which deselects the annotation), Tab, Ctrl+Enter or Esc, which both leave the field and keep the text. Nothing discards it; undo takes it back (one step).
- Picking an annotation in the list scrolls the page to it with a 140 ms glide (Settings: "Smooth scrolling to annotations", on by default; reduced motion turns it off). A long way starts two screens from the annotation. Scrolling or clicking stops the glide.
- Resting the pointer on an annotation shows its comment in a tooltip, text only with its line breaks, at most 12 lines. It follows the pointer, below it, with its tail pointing up at the pointer from just under the cursor's arrow; it shifts left, or goes above the pointer (its tail then pointing down), to stay wholly inside the page area. The delay is a Settings slider (0 to 2 s, 0.3 s by default). Text boxes show none, since their text is on the page.
- Comments' line breaks (CR, as Acrobat writes them, CR LF, LF, U+2028, U+2029) all show as breaks. A comment is written back only when its text was edited, so looking at one in a field changes nothing.
- Repair counts `/Rect` as too small only past the 1 pt margin. Unreadable QuadPoints are reported and left alone.
- Annotating a turned page places notes, drawings, text boxes and area highlights upright as seen on screen (text boxes carry `/Rotate`, as Acrobat writes); text markup follows the text. That holds for a page the document rotates and for one turned on screen only (the view rotation, a page's own turn: section 6.1): a text box typed there is typed upright as the page is shown, grows downwards there, and carries the page's `/Rotate` plus the turn (`Body::FreeText.turn`), as Acrobat writes for a box typed in a rotated view; an area highlight's corners are ordered as seen there; a note's icon goes below and right of the click as seen there. A text box is edited as its text stands: the editor is turned with it, and it is fitted to its text by its own `/Rotate`, whatever the page's is. A note's icon is drawn with the page, so on a page turned on screen only it lies on its side in Lectrix, as PDFium and pdf.js show it on a rotated page; Acrobat keeps it upright.

### 6.6 Settings, About and installers

- **Settings** (File menu, Ctrl+,): groups as tabs with icons down the left side (Up and Down move between them; the last one shown opens again while Lectrix runs; the fill of the one shown glides to the tab picked, and its settings rise a little as they fade in, both in 140 ms, at once with reduced motion), the chosen group's settings at the right, one per row: the name and a description, then the control, a switch for anything that is on or off, a dropdown for a choice, and a pill of segments (a radio group; arrow keys move and choose; the raised mark of the one chosen glides to it in 140 ms) for a choice between a few peers. **General:** author name; whether Lectrix checks for updates automatically, once a day (on by default); under Documents, the page display documents open in (section 6.1: single page continuous by default, any scroll mode, or as the document asks) and whether files that claim PDF/A open for reading only (on by default, section 5.4); under Selected text, whether selected text shows handles on its sides (off by default, section 6.1); under Search, whether the matches of a search are marked beside the scrollbar (on by default, section 6.1); under Links, whether the link under the pointer is tinted, and whether a tooltip says where it leads (both on by default, section 6.1); under Reset, **Restore defaults…**, a button in the destructive colour (the red of errors, as is the one that confirms), which asks first ("Restore default settings?": Restore defaults or Cancel) and then puts every setting back to its default at once, the shortcuts and the author name included (recent files, panes and the window's place are not settings and stay). **Appearance:** the theme, as three segments with icons (System by default, Light or Dark); under Motion, smooth zooming (on by default, section 6.1) and smooth scrolling to annotations picked in the list (on by default, section 6.5), to the next and previous page with the view bar's buttons (on by default, section 6.1) to the places bookmarks and links in the text lead to (on by default, section 6.2) and to the next and previous match of a search (on by default, section 6.1), a switch each; under Visual adjustments, how the pages of every document look (section 6.1): Brightness, Contrast and Sepia (sliders, as in the viewer's panel), Invert colours and Greyscale (switches), all as the pages are by default, and **Reset**, which puts them back so (disabled while they are). They apply at once to every open document that has no adjustments of its own, in every window. **Annotations:** whether new text markup opens its comment (off by default, section 6.5); whether new annotations take the last color given to an annotation, and the last opacity given to their type (on by default, section 6.5); the comment tooltip's delay, which the tooltip on a link has too (a slider, 0 to 2 s, 0.3 s by default, section 6.5); under Colours, whether a colour button opens its panel when the pointer is on it (on by default, section 6.5), the 18 preset colours as the panel shows them, each a button that opens the colour picker to give that preset another colour (with a button there to put its default back; a changed preset is named by its hex value), and **Restore colours**, which puts all the defaults back. Only presets that differ from the defaults are stored (a preset's place and its colour), so a later version's new defaults reach the others. **Toolbars:** the annotation toolbar's placement (docked beside the pages by default, always shown, or floating over them); for the docked toolbar, where it is docked (at the top by default, in the bar above the pages, or at the left or the right of them, in a bar of its own; shown, but not changeable, while the toolbar floats); for the floating toolbar, its edge (bottom by default, top, left or right) and whether it shows only while the pointer is within about 72 px of that edge, while it has keyboard focus, while a panel or list one of its controls opened is open, and for 1.5 s after a tool is picked (off by default), both of which can be changed while the toolbar is docked too, since full screen floats it (section 6.1; their descriptions then say so). At a side, docked or floating, the toolbar's controls are stacked (section 8). An install from before the toolbar was docked by default keeps it floating, as its app data says. Then the quick tools for selected text, a switch each. **Shortcuts:** every command that can have a keyboard shortcut (those of the menus and the annotation tools, with or without one by default), grouped as the menus are (File, Edit, View, Go to, Document, Annotation tools, Help), then the keys with a fixed use (Esc, Del, F2, Shift+F10, the arrow-key combinations, Ctrl+Enter, Alt held in full screen), which are listed but can't be changed. A search field above filters the rows by command, group or key. Each shortcut is a chip whose key is a button: pressing it, then the new keys, changes it; Backspace removes it and Esc leaves it as it was (and does not close Settings). A command can have up to three: the plus button at the end of every row adds one (a command without any shows only the plus), and a shortcut that was added, not one the command came with, has an x on its chip that removes it. There is no reset per command; **Reset all…** puts back the ones every command came with, after asking. Keys another command has are refused with that command's name, and so are keys with a fixed use (the keys that move the focus or edit text, Shift or Ctrl+Shift or Alt+Shift with arrows, Enter, F2, Shift+F10, Alt+F4, Ctrl+A, V and X). A change applies at once, and menus and tooltips show the keys in use. Whatever its keys, a command runs while a text field has the focus only if it did before (saving, finding, zooming, tabs...) and its keys include Ctrl or Alt or are a function key, never keys that edit text there (Ctrl+C, Ctrl+Z...). Only shortcuts that differ from the defaults are stored (a command's name and its keys), so a later version's new defaults reach the others. The groups and rows are declared once in `src/lib/features/settings/schema.ts`, which the dialog renders (the shortcuts have a panel of their own, and their commands and defaults are in `src/lib/shortcuts.ts`); a new setting is a field in Rust's `Settings` plus a row there, and a new command with a shortcut is an entry in `SHORTCUT_GROUPS`. Each change applies at once and is stored in app data (typed text once typing pauses or the field is left); there is no Save button, and the dialog closes with its close button or Esc.
- **About** (Help menu), centred: the app icon (96 px), the name, then the version and its author on one line ("Version 1.0.0 · by Mark Ingrem", `AUTHOR` in `src/lib/config.ts`), the name in the text's colour and in the accent under the pointer, opening the author's GitHub profile; then one paragraph with the AGPL notice and MuPDF's credit, and a "Source code on GitHub" button with the GitHub mark (Simple Icons) that opens the repository. Both open in the default browser: Rust opens them from addresses it holds itself (`WebPage` in `ipc.rs`, kept equal to the frontend's by a test), so the webview neither goes online nor can have another page opened. The dialog takes the focus as it opens; it closes with the button in its corner or Esc.
- **Updates** (ADR 0011): Lectrix asks GitHub for the latest release in the background once a day: after the startup files open when a day has passed since GitHub last answered a check (automatic or from the Help menu), and again each day while it stays open; a check that fails (offline) is tried again at the next start or within the hour. A newer one brings a floating notice, with a link to the changes it brings (What's new): Update, Not now (asked again at the next day's check) or Don't ask again (that version is never offered again; a later one is). Update downloads with a progress bar and Stop, and the download must pass the updater signature check. macOS and Linux then install it and offer Restart now or Later. Windows cannot replace the running app, so it offers Restart now (after the usual unsaved-changes prompts, in every window, the installer runs and opens Lectrix again) or Later (the installer runs when Lectrix closes). Failures of the automatic check are logged, never shown. **Check for updates…** (Help menu, above About) asks at any time, whether or not the automatic check is on, and offers a version skipped with Don't ask again: the notice shows "Checking for updates…" with a moving bar, then the same choices for a newer release, or a notification that Lectrix is up to date ("You have the latest version, 1.2.0."), or a plain error if GitHub can't be reached. While a notice is on screen it stays as it is; an update already downloaded and put off with Later brings back Restart now or Later instead of downloading again.
- **What's new** (Help menu, above Check for updates): the changelog (`CHANGELOG.md`) in a dialog, newest version first, each version's changes under the parts of the app they touch (start screen, viewer and tabs, annotations, bookmarks, page labels, combining files, settings, installation and updates, general), with bold the only formatting. The first start after an update (a newer version than the one that started last; not a first install) says so until dismissed or followed: on the start screen, a block to the right of the app's name ("Updated to 1.1.0", See what's new); with documents open, a notification ("Lectrix was updated to 1.1.0", What's new). Before updating, the update notice's "See what's new" opens the same dialog with the changes since the installed version (from `latest.json`, in English) and Update at the bottom. A translation of the changelog (`CHANGELOG_RU.md`…) is shown for the app's language, and English for any version it lacks. How to write it: `docs/releasing.md`.
- **Releases** (ADR 0011, `docs/releasing.md`): a new version in `package.json` on `main` publishes a GitHub release once CI passes: Windows (the NSIS installer), Linux (AppImage, deb, and rpm for final versions) and macOS (Apple Silicon and Intel), with build provenance attestations and the updater's signed `latest.json`, and the version's part of `CHANGELOG.md` as the release's description. Versions follow semver, a pre-release as `1.0.0-beta.1`, and installers are built with `npm run bundle`.
- **Installers:** Windows has one, the NSIS setup program (ADR 0007, ADR 0020). It asks first (ADR 0015): "Install for anyone using this computer" (Program Files; preselected for an administrator) or "Install just for me" (`%LOCALAPPDATA%\Programs`), as Tauri builds it, so an administrator answers a UAC prompt when it starts, updates included; an update keeps the earlier choice and folder, and silent installs take `/AllUsers` or `/CurrentUser`. It has a "PDF files" page after the folder page, "Open PDF files with Lectrix", checked by default. It registers Lectrix for PDFs (Open with, Default apps), with the Lectrix PDF icon (`lectrix-pdf.ico`, installed next to the app) for PDFs it opens; Windows asks which app to use at the next PDF, and the installer never takes over the default itself. For silent installs, `/NOPDF` leaves the registration out. It installs `LICENSE.txt` and the license notices. The setup program and the uninstaller it installs have the app's icon as their file icon (`installerIcon`, `uninstallerIcon`). Versions up to 1.1.0 also had an MSI, which installed for everyone: a copy installed from it updates through the setup program, which removes the MSI install first, asking nothing, installs into Program Files as the MSI did, and keeps whether it was registered for PDFs. The Linux deb and rpm install AppStream metainfo (`src-tauri/linux/org.lectrix.pdf.metainfo.xml`, to `/usr/share/metainfo`) beside the desktop file and the icons: software stores (GNOME Software, KDE Discover) list an installed app from it, with the icon the desktop file names, and show a bare package without an icon when it is missing. The desktop file's category is Office (`bundle.category`).

### 6.7 Organize pages

A document's pages as a grid, to put them in another order, rotate them, delete them, add pages from another file and copy pages into a new one. Each change is made in the document at once (ADR 0018).

- **A mode of the document's tab.** **Document > Organize pages** (a command without a default shortcut) shows the pages as a grid in the viewer's place, with a bar of its own in the view bar's place. The view bar has no button for it: the menu has the command, and the start screen the tool (section 6.1). The tabs and the banners stay. The side panes, which are for reading, are not shown meanwhile, nor are their buttons; they come back as they were. **Done** in the bar, Esc once nothing is selected, or the command again (its menu item reads **Finish organizing pages** meanwhile) go back to reading where the document was; Enter or a double-click on a page goes back to reading at that page.
- **The grid** is the Combine view's (`PageGrid.svelte`, section 6.4): a click selects a page, Ctrl+click adds or removes one, Shift+click extends, a rectangle drawn from anywhere but a picture selects what it touches, arrow keys move the focus (Shift extends) and Ctrl+A selects every page. Under each page is its label, with its place in the document after it where that says something else ("iv (4)"; "(4)" for a page whose label is empty). Under the pointer, a page's label gives way to a bar in its place, centered under the picture, as in the Combine view: the same label, then buttons that rotate that page counter-clockwise and clockwise and delete it.
- **The bar**, centered as the view bar is: rotate counter-clockwise and clockwise, delete; then **Insert**, **Extract** and **Labels**, each with its name beside its icon (pages from a file, the selected pages into a new document, the Page labels dialog); smaller and larger pictures (steps from a 96 px square, each about a third larger than the one before, up to the size at which one page fills the view; 160 px at first); how many pages there are, or are selected ("3 of 212 pages selected"); and at the end **Done**.
- **The size of the pictures** also changes with Ctrl+= and Ctrl+- (the commands that zoom the pages while reading; a step of the sizes, as the buttons), with Ctrl and the mouse wheel (a notch is about a fifth larger or smaller) and with a touchpad pinch, which follows the fingers to any size between the smallest and the largest. A size from a button, a key or a wheel notch glides there in 140 ms, as zooming the pages does (section 6.1; at once when Settings' smooth zooming is off, or with reduced motion). The page under the pointer keeps its place for the wheel and a pinch, the page in the middle of the view for the buttons and the keys. The largest size is the one at which a single page, with its label under it, fills the grid's view, so it follows the window: there the pages come one under another, as while reading, and pictures larger than a window made smaller allows take its largest size at once.
- **Move:** drag the selected pages by a picture to a gap between pages, or Alt+Shift with an arrow key for one place at a time (pages apart come together). Links and bookmarks keep leading to their pages. Page labels belong to the places: a moved page takes the label of its new place, and the label ranges stay as they are.
- **Rotate:** the bar's buttons and R and Shift+R turn the selected pages in the document (`/Rotate`); the buttons under the page the pointer is on turn that page alone.
- **Delete:** the bar's button, Del or Backspace, or the button under the page the pointer is on. Lectrix asks first ("Delete page iv?" naming the page as the page box does, or "Delete 3 pages?"; **Delete**, in the destructive colour, or **Cancel**, which Esc means). With the pages go the links and bookmarks that lead to them (a bookmark with bookmarks inside stays as a heading), the named destinations that lead to them and the form fields on them; label ranges after them start that many pages earlier, so the numbering closes up, and a range left without pages goes. At least one page stays. A notification then says how many pages were deleted, what went with them, and that the pages stay inside the file, where they can be recovered, until it is saved with Save As (optimized), with a button that does that: an ordinary save adds to the file and keeps what was there (section 5.4).
- **Insert pages from files** (section 6.4): the bar's button, or the command, asks for one file or several, then for the options, and puts their pages after the last selected page (after the page with the keyboard focus when none is selected). The menu puts them before or after the selected pages. PDFs dragged in from another program show the gap under them, as dragged pages do, with a note at the top of the grid ("Drop a PDF between two pages to insert its pages there"); dropped, their options are asked and their pages go into that gap. The inserted pages are then selected, ready to be dragged elsewhere.
- **Extract:** the bar's button, or the menu, copies the selected pages into a new document, in the order they have in the document. Nothing is asked first: Lectrix shows progress with Stop, then opens the new document in a tab of its own, with its pages as a grid (at the size this grid has), so they can be put in order at once. It is named "Pages from report.pdf" and is no file yet (section 7, documents without a file): its tab is marked unsaved, and Save asks where to save it, starting next to the document. The document keeps the pages and is not changed, so this works in a document open for reading only. The pages go as the document has them now, unsaved changes included, with their annotations, the links among them, the bookmarks that lead to them (flat) and their page labels; links and bookmarks that lead to pages left behind are not copied, and a notification says how many.
- **Page labels** (section 6.3) are set in a dialog over the grid, where each page shows its label: the bar's **Labels** button or the grid's menu opens it, for the selected pages. Nothing offers it while reading.
- **Menu:** a right click on a page, or Shift+F10 with the keyboard focus on it, offers what can be done with the selected pages (a page that is not selected becomes the selection first): Rotate clockwise, Rotate counter-clockwise, Delete page… ("Delete 3 pages…"), Extract page into a new document, Insert pages from file before…, Insert pages from file after…, Page labels…, and Read from this page.
- **Undo and redo** are the document's (section 7): each move, rotation, deletion and insertion is one step ("Move pages", "Rotate page", "Delete pages", "Insert pages"), in the grid and while reading alike.

Settled details:

- Starting the mode leaves full screen, picks the Select tool, closes the search and deselects text and annotations. The grid opens with the current page in the middle of the view and the keyboard focus on it. Meanwhile the commands that are for reading do nothing, and their menu items are disabled: Find, the annotation tools, Full screen, the panes and their panels, fitting, the page display, rotating the view, Go to page, Back and Forward and Add bookmark.
- The mode belongs to its tab, stays while another tab is shown, and is not remembered: a document opens for reading.
- What is kept by page follows its page through every such change, an undo or a redo included (`DocumentChange.pageMap`, `PageMove` in `src/lib/stores/pagemap.ts`): the viewer stays on the page it showed (on the page that took its place if it was deleted), the history of jumps follows its pages and forgets the places on deleted ones, and a selected annotation stays selected.
- A page keeps its cell in the grid, and the picture in it, while the pages around it change: the picture is drawn again for the new revision under the old one.
- The pictures show the pages as the file has them, without the document's visual adjustments, as the Combine view does.
- After a deletion, the page that followed the deleted ones is selected.
- When the Insert command showed the grid itself, giving the insertion up (no file chosen, its password not given, Cancel in the dialog) goes back to reading. The Pages panel's "Insert pages from file after this page…" does the same with the gap after that page.
- Of several files, those that cannot be used are left out and the rest go in: one that fails to open or forbids copying its content says so in a notification, and one whose password is not given is skipped; the options are asked once every password prompt is answered. If a file fails to go in, the ones before it stay and the notification counts them. Files dropped while an insertion is under way are not taken. Files dropped on the window while the grid shows are never opened in tabs.
- A document that forbids copying its content can't have pages extracted, and says so. Stopping an extraction leaves nothing behind. Pages can be extracted from a document that is itself not saved yet.
- An Esc that closes a menu or a dialog does only that: it neither deselects nor leaves the grid.
- Edits run one after another, each working out its pages when its turn comes, so a key held down cannot overtake itself.
- The pictures are rendered for the size a glide ends at, or a pinch rests at (150 ms after its last move): once, not for every frame on the way, during which the pictures they have are stretched.
- A document open for reading only (section 5.4), or whose permissions forbid assembling it, shows its grid, where pages can be selected and nothing changes them: the PDF/A banner says why, or the bar does ("This document’s security settings don’t allow changing its pages."). A signed document gets the usual warning before the first change.

## 7. Document model, undo/redo and saving

The Rust session is the single source of truth: the frontend holds only a view of it, and the undo history lives in Rust.

**Operations.** Every change is a variant of one `Operation` enum in `ops.rs` (for example `AddAnnotation`, `UpdateAnnotation`, `DeleteAnnotation`, `AddBookmark`, `SetPageLabels`, `RotatePages`, `MovePages`, `DeletePages`, `InsertPages`, `RepairAnnotations`). Applying an operation increments the document revision and returns what changed. The session reads again only what the operation can have changed: the whole outline, which takes a tenth of a second in a file with thousands of bookmarks, only after bookmark edits and after pages are deleted or inserted (`OutlineEffect` in `ops.rs`, ADR 0018).

**Undo/redo.** Uses MuPDF's built-in journalling, wrapped in `ffi/journal.rs`; each `Operation` is one journal step with a human-readable name ("Add highlight", "Rename bookmark"). The Edit menu shows the name of the step being undone or redone. Saving reopens the file, so undo history starts again after each save (ADR 0003); after a crash restore it starts at the restored state (MuPDF cannot load a saved journal, ADR 0001).

**Dirty state.** A document is dirty when its revision differs from the last saved revision. Show a dot in the tab (a spinning ring while saving; there is no status bar), and prompt when the tab closes, when its window closes and on app exit.

**Documents without a file** (ADR 0019). Pages extracted into a new document (section 6.7) open as a document that is no file yet. Its tab has the name it would be saved under ("Pages from report.pdf"), the unsaved dot from the start, and "Not saved yet" as its tooltip. Save asks where to save it, as Save As does, starting in the folder of the document its pages came from; saved, it is that file and a document like any other. Closing its tab, its window or the app asks first ("Pages from report.pdf has not been saved yet. Do you want to save it?": Save, Don't save or Cancel). Until it is saved it is not among the recent files, has no remembered view, is not watched and has nothing to reload; undoing every change leaves it unsaved. Its pages are in a working copy in the app's local data folder (`unsaved/`, beside the recovery copies), which goes when the document is saved or closed, and at the next start if Lectrix did not end normally. Crash recovery covers it as any document with unsaved changes, and restores it as a document without a file.

**Atomic save.**

1. Write the new file to a temporary file in the same folder as the target.
2. Flush it to disk.
3. Replace the original in one rename on the same volume.
4. On failure, delete the temp file and leave the original untouched.

A failed save also leaves the document in memory as it was, so saving again (or Save As) is safe: an incremental save is written without moving the document on to the update it wrote, and "Save As (optimized)" optimizes a copy of the document (ADR 0003, "A save that fails").

Documents are opened through a file stream that allows that rename (ADR 0003). On Windows the rename is retried for up to a second while a file is locked, since antivirus scanners and the search indexer open a file just written for a moment. If the target is still locked by another program (Acrobat locks files it has open), show a clear message naming the likely cause and offer Save As.

**Crash recovery.** Every 2 minutes, each dirty document whose content changed since its last copy gets a recovery copy in the app's local data folder (a snapshot with the unsaved changes as an incremental update; damaged files are copied in full). Saving, reloading or closing a document deletes its copy, and so does quitting normally. On the next launch, before opening startup files, Lectrix offers to restore copies a crash left behind: Restore, Discard (asks once more) or Not now (asked again next time; Escape means Not now). A restored document opens in a tab for its own file, marked unsaved, and saves incrementally onto it. Encrypted files ask for their password again.

**External changes.** Watch open files. If a file changes on disk and the document has no unsaved edits, offer to reload; if it has unsaved edits, warn and offer Save As.

## 8. UI and UX guidelines

The app should feel like a native Windows 11 app: calm, fast, and keyboard-friendly, with the document always the visual focus.

**Layout.**

- **Windows:** a tab can have a window of its own, and windows exchange tabs. Dragged off its row (24 px above or below it, or out of the window at a side), a tab is on its way out: a stand-in with its name follows the pointer while it is over the window, the tab waits dimmed in its place, and going back to the row takes it up again. Dropped on another Lectrix window, it joins that window's tabs at the end and is shown there; dropped anywhere else, it gets a new window with its title bar under the pointer, the size of the one it left. Esc ends the drag and the tab stays. The tab's context menu and File > Move tab to new window (a new window a little down and right of the first; a command without a default shortcut) do the same from the keyboard. The document goes as it is: unsaved changes, undo history, its place, zoom and page display; nothing asks to save. A window's only tab can't go to a new window (it would be the same window again), but it can go to another one. A window left with nothing to show closes; one that still has the Combine view stays. Every window is the whole app (menus, start screen, Settings, its own Combine view), and none is the main one: closing a window asks about its own unsaved documents and closes them, Lectrix quits with its last window, and File > Exit closes them all, each after its own question (Cancel in any of them keeps that window and the one Exit was picked in). Settings apply to every window at once, and the recent files are the same in all. The taskbar names each window after what it shows ("report.pdf - Lectrix"; "Lectrix" on the start screen).
- **Window:** Lectrix starts where its window was when it last closed (with several windows, the one used last): the same size and position as a normal window, maximized if it was (then Restore goes back to that size), never minimized. Kept in app data with the panes; a place on a monitor that is no longer there, or with the title bar out of reach, is dropped and Windows places the window. The window is made there, so it never shows at the default size first.
- **Title bar:** custom (explicit drag region), holding the app's icon and name at the left, the menus, the document tabs and the window buttons, placed and drawn as each platform's own apps have them (ADR 0021): on Windows drawn by the app at the right (Tauri decorations off), as Windows draws them; on Linux drawn by the app in Adwaita's style (round, 24 px, a faint fill), the buttons and the end GTK's decoration layout names (GNOME: close alone, at the right); on macOS the system's own traffic lights over the bar's left end, which leaves 80 px for them (none in a full-screen space, where the system hides them). On macOS the menus are not in the title bar but in the system's menu bar, arranged as Mac apps arrange theirs (`menus.svelte.ts`, laid out once for both; `menu.rs`): the application menu (About, Check for updates, Settings, Services, Hide, Quit), File, Edit (Undo and Redo, which edit a focused text field's text too, then the system's Cut, Copy, Paste and Select All, and a Find submenu), View, Document, Window (Minimize, Zoom, the tab commands, Bring All to Front) and Help, with labels in title case. Each window sends its menus as they change, and the menu bar shows those of the window in use. While a dialog is open, the menu bar offers nothing that acts on the window. The bar is measured as VS Code's title bar (35 px tall, 16 px icon in a 35 px box, 12 px name, 13 px menus). The icon and name are one button, which shows the start screen while something is open (section 6.1; filled under the pointer; plain while the start screen shows, with the pointer on it or not, since there it is where one is) and still moves the window when dragged; with nothing open it only moves the window.
- **Side panes** hold three panels: Pages (thumbnails), Bookmarks and Annotations (the annotation list). The left pane, open by default, starts with the first two; the right pane, closed by default, with Annotations. Each pane's top row, with a line under it, has its panels' tabs (icons with tooltips and accessible names, drawn as the annotation tools are: the panel shown has the active tool's mark, which glides to the tab picked in 140 ms, at once with reduced motion) and, at its outer end, the button that hides it. A closed pane's button stays in the same place, at that end of the view bar's row, as in Obsidian. Panels move freely: a tab is dragged along its row, into the other pane's row, or onto a closed pane's button; Ctrl+Shift+Left/Right and the tab's context menu do the same from the keyboard, crossing between the panes at their inner ends. A panel moved into the other pane is shown there; a pane left without panels closes, and its button goes until a panel is dragged to the drop place shown there.
- **View bar**, one bar at the top of the document as in Acrobat, in the side panes' colour and continuous with their top rows (the line between a pane and the page starts below them), its contents centered: previous page, next page, the page box with the page label or number and the physical position after it ("iv" then "(4 of 312)", or "4" then "of 312"; an empty box then "(4 of 312)" on a page whose label is empty, section 6.3; screen readers hear "iv (4 of 312)"), then zoom out, the zoom level (a menu with fit width, fit page and the presets) and zoom in, then the page display (a menu of the scroll modes and the cover page, section 6.1), then the visual adjustments (a panel, section 6.1), then the annotation tools when docked there (Settings). Previous and next page go to the top of that page (in the two-page modes, the next row), gliding there (section 6.1), and are not recorded in back/forward history. In a narrow window the bar wraps onto a second row.
- **Center:** the page canvas, below the view bar. The annotation toolbar is docked or floats (Settings). Docked, it is in the view bar, or in a bar of its own at the left or the right of the canvas: in the view bar's colour, from the view bar down, between the canvas and that side's pane, with a line between it and the pages. Floating, it lies over the canvas, centred along its bottom, top, left or right edge (at the right, clear of the pages' scrollbar). Its colour button comes first, before the tools (after the page and zoom controls in full screen). At a side, docked or floating, its controls are stacked: the colour, then the tools one under another, then the style controls the tool brings. There the colour button shows the colour alone and a size's button its number alone ("2" for 2 pt; the list names the sizes in full), each as wide as a tool, and what a control opens (the colours, a list of sizes) goes beside the toolbar, over the pages, never over the tools under it. Where the canvas has less height than a stacked toolbar needs, the toolbar scrolls, with no scrollbar of its own. The search bar and the bookmark inspector move below a floating toolbar that stays at the top, and beside one that stays at the right. The active tool has an accent icon and an accent border on every side; so do the type buttons of a selected annotation. Picking another tool (or type) glides that mark to it in 140 ms, and the style controls the tool brings (stroke width, font size) slide open after the tools (beside them, or under them in a stacked toolbar); reduced motion does both at once. Full screen (section 6.1) shows the page canvas alone, on the whole screen, with the toolbar floating and the side panes over the pages when something brings them.
- The Annotations tab carries the "needs repair" dot, and so does its pane's button while that pane is closed.
- **Inspector**: for a bookmark, floating over the right edge of the page (section 6.2); for an annotation, a panel beside it on the page that can be dragged and resized (section 6.5). Shown when opened for it; an annotation's, like its bar, is not shown while the annotation list shows its row, which has its controls and its comment.
- **Side panes** resize by dragging their inner edge, or from the keyboard on that edge (arrows, Home, End); a double-click resets the width. Each takes at most 40% of the window. Every other pane beside the pages resizes the same way, with the same edge (`PaneResizer.svelte`), and has its width remembered: the Combine view's files (section 6.4). Which panes are open, their widths, the panels each holds and the one each shows are remembered in app data. Opening and closing slides (140 ms); a fit-width or fit-page view re-fits as a pane moves and renders again once it stops.

**Visual style.**

- Colours from Neo, the Obsidian theme: its light theme and its Midnight dark theme, with the greys tinted to Lectrix blue's hue, solid throughout (no Mica; ADR 0014).
- Follow the system light/dark setting by default; Settings can force light or dark. The accent is Lectrix blue from the brand kit (ADR 0010): `#2F5DAA` in the light theme, `#6FA3EF` in the dark one.
- As in Neo: document tabs are pills, the active one raised; menus, popovers and dropdown lists are flat, with a thin edge and no shadow; a notification, and the update notice above them, has the thin edge and a slight shadow (`.notice`), which lifts it off the pages it lies over; clickable controls show the hand cursor (the window buttons keep the arrow). A coloured button (the primary one, filled in the accent, and the destructive one, in the red of errors) stays in its colour under the pointer, a shade further from its text: darker under the light theme's white text, lighter under the dark theme's dark text (`--lectrix-accent-hover`, `--lectrix-danger-hover`). A menu item whose submenu is open, and a button whose menu or panel is open, keep the tint they have under the pointer while the pointer or the focus is in what they opened. Dropdowns are the app's own (`Dropdown.svelte`), never the native `<select>`, whose list the system draws in its own colours. Sliders are too (`Slider.svelte`, for every slider: the comment tooltip's delay, an annotation's opacity): a thin track with no outline, filled up to the handle in the accent, as a switch that is on, and a round handle in the colour of that switch's thumb (white, in the dark theme as in the light one) with a thin edge in the accent and a slight shadow, each colour a token of its own. The fill and the handle glide to each new step in 100 ms.
- Tooltips are the app's own as well (`Tooltips.svelte`): a control names its tooltip in `data-tip`, never in `title`, which the system would draw in its own style (a test checks that no component has one). A tooltip is flat, in the menus' colour with their thin edge, and has a small tail with curved sides, as the comment panel's, pointing at its control. It goes below the control and centred on it, above it when there is no room below, beside it when there is none above either (a pane's edge), and stays inside the window; for a control wider or taller than 320 px (a row, a pane's edge) it goes where the pointer is along it, clear of the cursor's arrow. It shows once the pointer has rested on the control for half a second, or when Tab or an arrow key brings the keyboard focus there, and at once within 0.4 s of another tooltip going; it fades in in 100 ms. A press, a key, scrolling or leaving the control takes it away, and after a press or a key it stays away until the pointer leaves that control. Screen readers get a focused control's tooltip as its description, unless it only repeats the control's name. An annotation's comment tooltip (section 6.5) has the same look.
- Font stack: Google Sans, bundled with the app (ADR 0009), then Segoe UI Variable, Segoe UI and the system UI fonts for characters it lacks.
- Spacing on an 8 px grid (4 px for tight spots); corner radius 6–8 px; thin borders instead of heavy shadows.
- All colors, sizes and radii as CSS variables (design tokens) consumed by Tailwind; no hard-coded colors in components.

**Behavior.**

- Never block the UI thread. Long operations (combining, repair, saving a large file) show progress and can be canceled.
- Placeholder page shapes at the correct size while pages render, so the scroll position never jumps.
- Errors in plain language with a suggested next step; never show raw error text or crash on bad input. Log details to a rotating log file.
- Respect reduced-motion settings; keep animations under 150 ms.
- Notifications come and go in 140 ms (`noticeMotion` in `components/notices.ts`), by a zoom, not a slide: one is where it belongs from its first frame, and grows there from 90% of its size as it fades in; dismissed or timed out, it shrinks to that as it fades out. Its place in the column opens ahead of it and closes after it, so the ones above it make way and close up without a jump. The update notice comes and goes the same way.
- A dialog comes in in 140 ms: it rises 8 px into place as it fades in, while the window behind it dims. It goes the same way back in 100 ms, and takes no clicks meanwhile. On macOS a dialog is a sheet instead (ADR 0021): it comes down 16 px from under the title bar into place just below it, centred across the window, over a light dim, with 12 px corners and 28 px buttons, the main one at the right; a question is an alert as macOS lays them out (the app's icon over a centred title and message, buttons as wide as the alert, two side by side with the main one at the right, more stacked with it on top and Cancel at the bottom), and Return presses the main button. It goes on showing what it showed (`held` in `components/held.svelte.ts`): the question that was answered, the progress last reported; what its buttons and forms act on is gone by then, so a second press does nothing.
- Progress bars are one component (`ProgressBar.svelte`: copying pages into a new file, checking for an update, downloading one): the filled part glides to each new value in 140 ms, and a sheen runs along it, so the bar is seen to be at work between two values too; while how far is not known, a third of the bar runs from end to end. These two go on for as long as the work does; reduced motion stills them.

**Accessibility.** Every control is reachable by keyboard with a visible focus ring (the page canvas, which takes focus to scroll from the keyboard, has none: a ring around the document is noise), has an accessible name, and meets WCAG AA contrast (checked by `src/lib/contrast.test.ts` in both themes). Shift+F10 and the Menu key open the focused control's context menu. App-wide shortcuts such as Ctrl+S work while typing in panel fields.

**Default shortcuts** (the commands' ones can be changed in Settings > Shortcuts, section 6.6; the keys for what has the focus, such as Esc, Del, F2 and the arrow-key combinations, are fixed). With a keyboard layout that types non-Latin letters (Russian, Greek...), letter shortcuts follow the key's place on a US keyboard, so Ctrl+Я is Ctrl+Z; Latin layouts such as AZERTY or Dvorak use the letter typed. ## 9. Testing strategy and interop harness

Interoperability is verified by machines on every commit and by a person before every release; neither replaces the other.

**Test corpus** (`tests/corpus/`, Git LFS, never modified by tests). Collect at least one file per category:

- rotated pages (90, 180, 270) and a CropBox with a non-zero origin;
- a damaged cross-reference table, an encrypted file, a signed file;
- a large file (1,000+ pages) and a scanned file with no text layer;
- CJK and right-to-left text;
- files with existing outlines, existing page labels, and form fields;
- annotations made by other apps, especially the ones that display wrongly in Acrobat (the user will supply these).

The corpus is still empty (`docs/status.md`); the geometric cases come from generated files (`pdf-core/src/testgen.rs`). Write test outputs to `target/test-output/`, never next to corpus files.

Real-world files the user owns but cannot publish (for example books from their Calibre library) form a **local corpus**: `tests/local-corpus/survey.py` profiles a library read-only, `select.py` copies one or two files per category into `tests/local-corpus/files/` and writes `manifest.json` (both git-ignored), and `crates/pdf-core/tests/local_corpus.rs` runs over them, skipping when they are absent (as in CI). The source library is only ever read, never written.

**Unit tests (`pdf-core`):** coordinate transforms for every rotation and CropBox case; quad ordering; label formatting (roman, letters past z, prefixes); outline serialization including Unicode titles; atomic save failure paths.

**Round-trip tests:** for each annotation type, create → save → reopen with MuPDF → assert every key the write profile requires, with the expected values. Same for outlines, labels and merges.

**Structural check:** run `qpdf --check` on every file the tests produce; any warning fails the test.

**Cross-renderer harness (`tests/interop/`):**

1. For each test output, render each annotated page with three independent engines: MuPDF (`mutool draw`), PDFium (through a small script using the `pypdfium2` package), and pdf.js (a Node script using `pdfjs-dist`).
2. Inside each annotation's `/Rect`, compare the render against the same page rendered without annotations. If any engine shows no visible change, the test fails: that annotation is invisible in that engine.
3. Compare engines against each other with a tolerance, and save diff images for any failure.

The suites keep the names they got during the build: `phase0` (labels, outline, merge and highlight from `pdf-cli`), `phase2` (bookmarks), `phase3` (labels), `phase4` and `phase4-local` (combining), `pages` (moving and deleting pages, named for what it checks), `phase5` and `phase5-local` (annotations and repair). SumatraPDF and similar apps are built on MuPDF and do not count as an independent check.

**Manual release checklist** (`docs/manual-checklist.md`, performed by the user before every release; the agent prepares the files and keeps the checklist current): open the interop sample files in Acrobat Reader, Edge, Firefox and Foxit; for every annotation type confirm it is visible, has the right color and opacity, appears in the comments list, prints, and can be edited and deleted. Then the installers, a real crash, and a Narrator walk.

**Frontend and end-to-end:** Vitest for stores and component logic; `tauri-driver` with WebdriverIO for the critical flows (open, highlight, add bookmark, set labels, combine, save, reopen, crash recovery, recent files, tabs and windows, full screen, organizing pages, and a keyboard-only accessibility walk). The end-to-end tests run beside a Lectrix the user has open and leave it alone: a test run (`LECTRIX_EPHEMERAL`) is an instance of its own, outside the single-instance hand-off, and the launcher ends only copies of the app under test (`tests/e2e/lib/app.mjs`). **Run them as CI shows the app before pushing** (`npm run test:ci --prefix tests/e2e`, one or more test files after `--`): CI's Windows runners ask for reduced motion and have a 1024 x 768 screen, where the window's page is 1028 px wide and the view bar wraps sooner, and a test written on a larger screen with animations on can fail there alone. The mode passes the browser its reduced-motion switch (`LECTRIX_BROWSER_ARGS`) and gives a window without a remembered place that size (`LECTRIX_WINDOW_SIZE`). A test of motion checks the way there only where motion is allowed (`matchMedia('(prefers-reduced-motion: reduce)')`), and where things end up either way.

**Debug menu** (development builds, or a release build run with `LECTRIX_DEBUG=1`; `LECTRIX_DEBUG=0` hides it): after Help, it shows each notification, notice and prompt on demand, worded as the app words them: the update notice at every stage, the note after an update (start screen or notification), information and error notifications, the notification that a save removed a PDF/A claim, the file-changed banner, the banner of a PDF/A file opened for reading only (the open document can't be changed until Enable editing or Clear all) and the crash recovery offer, plus Clear all. Rehearsals change nothing in Rust or on disk: the update notice's buttons work on a stand-in that pretends to download and to restart. The rehearsed update brings what `CHANGELOG.md` lists under Unreleased, so the next release's notes can be read as users will see them. A new kind of notification gets an item there (`src/lib/features/debug/`).

**CI** (GitHub Actions): on `windows-latest`, five jobs. `checks`: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `svelte-check`, Vitest and the license check. `build`: the release app, its installer (uploaded as an artifact), `pdf-cli` and `tauri-driver`, once. On that build, side by side: `interop` (the interop harness), `installer` (a silent install/uninstall check of the installer, which also has it take over an install made by the 1.1.0 MSI) and `e2e` (the end-to-end tests). Every job, and every step of `checks`, runs whatever the others do, so one run reports every failure, and a job that failed is run again by itself (Re-run failed jobs), not with the rest. macOS and Linux jobs build the app and its tests and run the tests without failing the job. After CI passes on `main`, the Release workflow publishes a version that has no release yet (ADR 0011).

**Soak run** (`.github/workflows/soak.yml`, `tests/soak/run.mjs`): the end-to-end tests and the Rust tests ten times over, each pass to its end, then one list of every test that failed in any pass, with how often and why, on the run's page. It finds the tests that fail only some of the time, which a CI run shows one at a time, on the day each happens to fail. Started by hand (Actions > Soak), and every night when `main` changed that day; it gates nothing. Run it before a release, fix what it lists in one commit, and run it again. Locally: `node tests/soak/run.mjs --passes 3 --like-ci`.

## 10. Working rules for the agent

Follow these rules in every session; when a rule and a convenience conflict, the rule wins.

**Process.**

- Start each session by reading this document and `docs/status.md`.
- Work on one change at a time. For a new feature or a larger change, propose a plan and wait for the user's go-ahead before building.
- When a change is done and CI is green, report to the user: what was built, the tests, any measurements that changed, behavior choices made without explicit guidance, and decisions needed. Then stop for review.
- Add every change users will notice to `CHANGELOG.md`, under `## Unreleased`, in the commit that makes it, worded as `docs/releasing.md` says.
- Keep the docs current: `docs/status.md` (add gaps you find, remove gaps you close), `docs/versions.md`, `docs/interop-profile.md`, `docs/manual-checklist.md`, and this document when the product's behavior changes.
- Make small commits using Conventional Commits (`feat:`, `fix:`, `test:`…). Every commit builds and passes tests.
- When you deviate from this document, write an ADR in `docs/decisions/` first, explaining what, why, and the alternatives considered.

**MuPDF.**

- Never guess MuPDF function names or behavior. Check the pinned version's headers (`third_party/mupdf-include/`) and documentation before using any API.
- Where the `mupdf` crate lacks an API, add the smallest safe wrapper in `pdf-core/src/ffi/`, with a `// SAFETY:` comment on every `unsafe` block and a test for the wrapper.
- Changes to the vendored crate are listed in `third_party/mupdf-rs/LECTRIX_PATCHES.md`; changes to MuPDF itself go through the `mupdf-rs` fork (ADR 0008), with a plain patch in `docs/upstream/`.
- Keep `pdf-core` free of any Tauri dependency.

**Code standards.**

- Rust: no `unwrap()` or `expect()` outside tests unless the invariant is documented beside it; errors via `thiserror`; no panics across the IPC boundary.
- TypeScript: strict mode, no `any`, IPC types generated from Rust only.
- Svelte: runes for state; feature code in `src/lib/features/<feature>/`.

**Dependencies.** Add a dependency only when it saves significant work. Note its license (must be AGPL-compatible) and its size impact in the commit message, and update `THIRD_PARTY_NOTICES.md`.

**Tests and data.**

- Never modify files in `tests/corpus/`.
- Never weaken the interop profile, a test, or a threshold to get a green build. Report the problem and the options instead.

**Stop and ask the user when:**

- a decision affects licensing or adds a non-trivial dependency;
- a UI or behavior question is not answered by this document;
- a request or idea falls outside the v1 scope in section 1;
- an acceptance criterion or target seems impossible as written.
